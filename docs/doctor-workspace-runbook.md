Актуализировано 29 октября 2026 года по `main` (`6c468f5`). [Текущее покрытие](status.md) и [результаты сверки](verification/2026-10-29-repository-state.md) отделяют код от версии опубликованного стенда. ## Быстрый просмотр

Нужны Node.js 24.x и npm. После клонирования или изменения lockfile:

```sh
npm ci --ignore-scripts
npm run dev:doctor -- --port 8768
```

Откройте `http://127.0.0.1:8768`. Кнопка «Открыть кабинет» создаёт только синтетические карты в IndexedDB текущего браузера. Изменения переживают перезагрузку страницы. Учебные данные не отправляются серверу. При недоступности API рабочий режим не подменяется учебным. Прежние изолированные примеры доступны по `#/examples`; прежняя демонстрация — по `#/legacy`.

Путь врача: «Пациенты» → «Новый пациент» → профиль → эпизод и оформленные согласия → «Запланировать приём» (либо «Приёмы» → «Создать приём») → «Начать приём» → четыре раздела → сводка → подтверждение. После завершения доступны дополнение, печать и запись следующего приёма. В карте расположены динамика, план, дневник, очередь событий, сообщения и документы. Архивирование требует причины и отсутствия открытых приёмов/событий.

## Навигация и общий контекст

В карте пять основных разделов: «Обзор», «Приёмы», «Лечение и план», «Наблюдение», «Документы». Внутри «Наблюдения» доступны динамика, дневник, события и сообщения; прежние прямые URL сохранены. Сводка обзора показывает последний самоотчёт и подтверждённый план. Кнопка приёма открывает существующий текущий/ближайший приём; новую встречу можно запланировать в разделе «Приёмы».

Общий [клинический контекст](clinical-context.md) хранит диагнозы, соматику, лекарства и аллергии с происхождением, отдельным подтверждением врача и историей версий. «Добавить клинический факт» создаёт непроверенные сведения; «Подтвердить факт» фиксирует отдельное решение. Прежние поля доступны через «Уточнить в карте» и показаны для разбора без автоматического подтверждения. Дата изменения профиля не подтверждает полноту анамнеза. При изменении контекста открытая проверка Авиандра становится устаревшей: текст назначения сохраняется, уточнения сбрасываются только отдельным действием врача.

«Внимание» содержит фильтры «В работе», «Срочно», «Просрочено», «Сегодня», «Все». Срочность берётся из существующего события; просрочка зависит от его срока и не повышает клиническую срочность. «Сегодня» использует календарную дату локального часового пояса. На телефоне блок внимания находится перед расписанием, основные переходы доступны снизу.

[Проверка внедрённого интерфейса и скриншоты](verification/2026-10-24-doctor-ux.md).

## Подготовительная проверка Авиандра

«Назначить препарат» в заголовке карты или «Лечение и план» → «Назначить препарат» → «Выбрать Авиандр». Для остальных записей плана используйте «Другая запись». Блок «Контроль и договорённости» показывает ближайший контакт и сохранённые указания; «Запланировать контакт» открывает настоящую форму записи на приём. В форме показаны сведения карты, эпизоды и история лекарственных назначений. Группа «Уточнения врача» открыта сразу; дополнительные ограничения, взаимодействия и функция почек раскрываются отдельно: свободный текст карты не интерпретируется автоматически. Результаты и основания доступны отдельно; проверка сохраняется с черновиком и видна перед ручным подтверждением.

Правила **не утверждены**. Они не разрешают и не запрещают назначение; дозировку и режим определяет врач. Изменение значимых сведений карты требует явного обновления контекста и повторной сверки уточнений. Сервер пересчитывает результаты при сохранении/подтверждении; внутренний снимок не выдаётся пациентским API. Источник, ограничения, проверки и снимки — в [отчёте](verification/2026-10-24-aviandr-plan.md).

## Серверный режим на локальном стенде

Нужны .NET SDK 10 и PostgreSQL 17+. SDK выбирается по `global.json`. `DOCTOR_DOTNET` позволяет указать исполняемый файл SDK; иначе используется локальный `.cache/toolchain/dotnet/dotnet.exe` либо `dotnet` из PATH. `DOCTOR_PG_BIN` указывает каталог утилит PostgreSQL; локальный резервный путь — `.cache/toolchain/postgres/pgsql/bin`.

Установка SDK и PostgreSQL выполняется из официальных дистрибутивов. Скрипт не загружает и не запускает сторонние установщики. На подготовленном Windows-стенде:

```powershell
npm run setup:doctor:local
$env:Doctor__SourceDirectory = 'D:\Downloads\drive-download-20261022T162704Z-1-001'
npm run dev:doctor:api
```

В другом терминале:

```powershell
npm run dev:doctor -- --port 8768
```

`setup:doctor:local` создаёт отдельный кластер в `.cache/doctor-server/data`, слушающий только `127.0.0.1:55442`, и БД `doctor_workspace`. Повтор не очищает данные. Учётная запись — `doctor@example.test`; случайный пароль находится в `.cache/doctor-server/local-config.json`, поле `doctorPassword`. Пароли не зашиты в приложение, не выводятся в лог и не включены в Git. Этот файл и весь каталог `.cache` предназначены только для локального учебного стенда.

API слушает `127.0.0.1:5080`. Vite проксирует `/api` на него; другой адрес задаётся через `DOCTOR_API_URL`. Веб-приложение и API работают на одном origin. Для существующей БД вместо локальной конфигурации задайте `ConnectionStrings__Doctor`; остальные параметры среды задаются явно. Создание учётной записи выполняется через `npm run provision:doctor` с `Provision__Id`, `Provision__ClinicId`, `Provision__Name`, `Provision__Specialty` (`psychiatrist`, `physician`, `patient`), `Provision__Email`, `Provision__Password`; пациентской записи дополнительно нужен `Provision__PatientId` существующей карты той же клиники. Операция предназначена администратору, публичной регистрации нет.

## Данные, доступ и контракт

- PostgreSQL хранит карты, связь врача с пациентом, версии, квитанции команд и аудит. Сервер проверяет клинику и активную связь при чтении/изменении. Переданные клиентом имя автора, клиника и право доступа не являются полномочиями.
- `commandId` сохраняется при повторе неизвестного результата; `expectedRevision` защищает от потери чужих правок. При конфликте редактор сохраняет местный текст, показывает сравнение и требует явного выбора. Черновик автосохраняется через 1,2 секунды; до подтверждения ответа показывается состояние сохранения.
- В активном окне карты обновляются каждые 10 секунд, при возврате фокуса и после сообщения другой вкладки. Это частота опроса интерфейса, а не гарантированное время медицинской реакции. Вне сети нет ложного статуса успешного сохранения.
- Завершённый приём неизменяем. Его снимок фиксирует имя пациента, измерения, подтверждённый план и направления. Дополнение имеет автора, дату и причину. Остановленное позже назначение не переписывает снимок.
- Отдельно учитываются согласия на помощь, данные, связь и раскрытие. Исходящее сообщение требует действующего согласия на связь. Запись документа в приложении не заменяет его юридическое подписание.
- [OpenAPI](contracts/doctor.openapi.json) и `api.generated.ts` генерируются командой `npm run contract:doctor` из общих типов. Ручное редактирование сгенерированного клиента запрещено. `npm run contract:doctor:check` обнаруживает рассинхронизацию. Авторизованный врач получает контракт по `/api/openapi/v1.json`.
- Пациентский API: `/api/patient/session`, `/api/patient/record`, `/api/patient/commands`; вход по коду использует `/api/patient/access`. Допустимы `report.add`, `report.patient`, `dose.patient`, `questionnaire.patient`, `message.patient`, `message.received`; patientId определяется сессией. Мобильный клиент подключён через `PatientConnectionProvider` и `patientChannel`, передаёт исходные факты и получает разрешённый план. Факт получения не равен клинической обработке события; [контракт и ограничения](contracts/mobile-server-web-contour.md) описаны отдельно.

## Исходные документы

`Doctor__SourceDirectory` указывает исходную папку без копирования ограниченных материалов в Git. `/api/sources/{id}/file` требует сессию врача, выбирает путь только из реестра, проверяет выход за каталог и SHA-256. При другой редакции — 409; при неподключённом файле — 404. В библиотеке видны название и редакция; статус и локатор раскрываются в сведениях об источнике. 17 Markdown-документов доступны для чтения через существующий авторизованный API; PDF/RTF открываются исходными файлами без преобразования. Исторические источники скрыты из списка, ссылки прошлых записей сохраняются. Проверка актуальности и утверждение клинического содержания сохраняются отдельно от технической доступности файла.

Пациентские документы сейчас вводятся текстом либо файлами `.txt`/`.md` до 100 KB с текстом до 20 000 символов. Извлечение основано на явных заголовках, сохраняет точную цитату; врач подтверждает каждый факт. Для скана/PDF врач переносит проверенный текст. Универсальный OCR/NLP и юридически значимое подписание не заявлены.

## Подготовка всех вариантов шкал

В карточке пациента «Наблюдение и шкалы» → «Динамика» кнопка «Добавить оценку» предлагает ответы на вопросы GAD-7/PHQ-9 либо внесение готового результата любой поддерживаемой шкалы. Ответы сохраняются существующим клиническим контуром; графики используют сохранённый балл и версию без повторного расчёта. Результат из приёма связан с ним и включается в неизменяемый снимок при завершении. Отдельный свёрнутый каталог «Другие формы шкал» сохраняет 18 подготовительных форм, сравнение до трёх вариантов и черновики; эти черновики не становятся измерениями автоматически. Устаревшая заглушка PHQ-9 скрыта, поскольку действующая форма доступна через основной вход.

Возраст создаваемой или редактируемой карты ограничен 18–120 годами включительно в форме, локальной модели и API. Имеющиеся записи не удаляются. Вкладка «Обзор» содержит данные пациента, тесты и рекомендации; «Лечение и план» — проекты и подтверждённые решения, назначения, приверженность, контакты и направления. Подтверждение проекта, принадлежащего рекомендации, доступно из «Обзора» по ссылке «Открыть рекомендацию».

Тексты исходных форм не распространяются в Git. Подготовка из предоставленного каталога:

```powershell
npm run prepare:doctor:forms -- --source-dir 'D:\Downloads\drive-download-20261022T162704Z-1-001'
```

Для КОП-25 дополнительно передайте `--s38-text <layout.txt>`: layout-текст первых двух PDF-страниц с маркерами `===== PDF PAGE N =====`. На текущем стенде использован текст, извлечённый при источниковом анализе. Без этого аргумента S38 сохраняет метаданные с предупреждением; вопросы не выдумываются. Переносы/колонки текста необходимо сверить с оригинальным PDF. Скрипт проверяет SHA-256 всех оригиналов и записывает формы и отчёт только в игнорируемый каталог `.cache/doctor-server/clinical-forms`. `--self-test` выполняет проверки извлекателя на синтетических примерах.

На локальном стенде каталог подключается автоматически. Для другого развёртывания задайте `Doctor__FormDirectory`; доступ к `/api/assessment-forms/{id}` есть только у врача. Без серверной сессии мастер позволяет занести ответы по номерам оригинала. Версия сохраняется как `source-<первые 12 знаков SHA256>-draft-1`; изменение ключа требует новой версии. Все подготовительные записи сохраняют статус `unapproved`, исходные ответы, пропуски, автора и аудит. Они не передаются в клиническую динамику, пациентский план или алерты. Утверждение не доступно через клиентскую команду.


## Миграции, резервная копия и откат

При старте `Store.Initialize` транзакционно исполняет `apps/doctor-api/Migrations/001_initial.sql` под PostgreSQL advisory lock. Автоматического runner для последовательного применения будущих `002_*` и последующих файлов сейчас нет: добавление такого файла само по себе не обновит БД. Следующее изменение SQL-схемы требует отдельной реализации, ревью и проверки миграции; уже применённую миграцию не переписывают. Разделение DDL- и runtime-полномочий также требует изменения порядка запуска, поскольку текущий API исполняет DDL самостоятельно.

`check:doctor:restore` рассчитан только на локальный учебный кластер: делает `pg_dump -Fc`, восстанавливает в новую БД `doctor_restore_verify_<timestamp>`, сравнивает количество и хеш содержимого семи таблиц. Исходная БД не перезаписывается. Запустите в окне без записи; если исходные данные меняются, проверка завершается ошибкой. Результат и dump остаются в `.cache/doctor-server` для проверки. Аудит входит в dump; сравнение его текущего хеша исключено, поскольку обращения чтения создают новые записи.

В рабочем окружении резервируются БД, каталог источников, ключи Data Protection и защищающий сертификат. Задайте расписание, срок хранения, шифрование, ответственного и проверку восстановления на отдельном сервере. При неудачной поставке остановите запись, сохраните новую копию и восстановите согласованную версию приложения/БД в новый экземпляр; не выполняйте автоматическое удаление истории или откат медицинских записей. Проверка локального dump не устанавливает согласованные RPO/RTO клиники.

## Условия рабочего развёртывания

Соберите веб `npm run build --workspace @psycho/web-doctor`, сервер `dotnet publish apps/doctor-api -c Release`. Раздавайте `apps/web-doctor/dist` и проксируйте `/api` с того же HTTPS origin. Не публикуйте Vite dev server. Настройте TLS, разрешённые хосты и доверенный прокси; приложение не доверяет произвольному клиентскому заголовку пересылки.

В Production обязательны `ConnectionStrings__Doctor`, сохраняемый `Doctor__KeyDirectory`, `Doctor__KeyCertificatePath` и при необходимости `Doctor__KeyCertificatePassword`. Без сертификата защиты ключей сервер прекращает запуск. Сессионные cookie — Secure/HttpOnly/SameSite=Strict, срок 8 часов; все мутации требуют CSRF. Секреты передаются средствами среды/хранилища секретов, не Git. Изменение `security_version` или `active` пользователя отзывает серверную сессию; отключение `care_relationships.active` отзывает доступ к карте.

До настоящих пациентов необходимы независимое ревью главы разработки, клиническая приёмка и утверждённые процедуры обработки данных и реагирования, перечисленные в R24. Не активированы непроверенные пороги, автоматические диагнозы, подбор доз и рекомендации конкретного препарата. Текст врача сохраняется как его решение. Реестр не выдаёт отменённый стандарт за действующее правило.

Карты пока хранят связанные коллекции в JSONB с полной историей версий. Это обеспечивает целостность текущего процесса, но нагрузочную ёмкость большой клиники ещё нужно измерить; для больших журналов последующая миграция должна вынести отчёты/аудит/сообщения в страницы отдельных таблиц. Произвольного ограничения общей карты в 4 MB нет. Серверные квитанции идемпотентности хранятся отдельно и не теряются после ста команд.

## Совместимость модели контекста и диагнозов (PR #35)

С 26 октября 2026 года жалобы и анамнез находятся в `profile.clinicalContext`, соматические состояния выбираются из учебного каталога, а диагнозы приёма хранятся в `visit.diagnoses`. Прежние `profile.conditions`, `visit.episodeId` и заменённые поля заметок больше не входят в контракт. Снимок подготовительной проверки Авиандра включает выбранные соматические состояния и диагнозы приёмов; изменение этих данных требует повторной сверки. Подтверждение диагноза сохраняет ограничение специальности психиатра.

Браузерный учебный режим открывает отдельную IndexedDB `syncli-doctor-synthetic-v2`. Прежняя `syncli-doctor-synthetic-v1` остаётся нетронутой, её записи не мигрируются и не показываются в новой версии. Начало новой учебной сессии не означает удаление старой базы.

**Серверные JSON-карты прежнего контракта автоматически не мигрируются.** Для проверки новой версии нужен отдельный пустой синтетический PostgreSQL-стенд. Нельзя направлять новую сборку на прежнюю БД и считать смену IndexedDB серверной миграцией. До обновления существующего стенда глава разработки должен согласовать перенос и резервное восстановление либо явно согласованный новый синтетический стенд. Реальные данные эта процедура не обслуживает.

При настройке отдельного стенда укажите отдельные каталог данных, порт, конфигурацию и `ConnectionStrings__Doctor`; не переиспользуйте рабочую БД. Для интеграционной проверки PR использован отдельный кластер на `127.0.0.1:55445`. Значения паролей остаются в игнорируемой локальной конфигурации.

Откат выполняется отдельным revert PR, возвращающим согласованные версии клиента, API и контракта. Для прежних серверных карт восстанавливается прежняя сборка и её БД; карты новой схемы нельзя отдавать старому клиенту. Браузерная база v1 сохранена. Полная выгрузка МКБ-10 и клиническое утверждение каталога не входят в эту интеграцию.

[Проверки интеграции и снимки интерфейса](verification/2026-10-26-doctor-pr35-integration.md).

## Оценка → решение → подтверждённое действие

[Синтетический контур MI03–MI13](clinical-workflow.md) доступен в обзоре карты и приёме через «Оценки и решения». Раскройте «Добавить данные», выберите сценарий и нажмите «Добавить сценарий» либо сохраните отдельный самоотчёт. Существующие записи не удаляются. В рабочем дне появится очередь решений; в плане и приёме используются те же рекомендации.

«Принять» создаёт проект; «Проверить и подтвердить действие» отдельно подтверждает план, выдаёт направление или датированное задание на самоопросник. Изменить/отклонить проект можно через рекомендацию до исполнения: прежний проект и причина сохраняются в истории. Обходить решение обычным подтверждением связанного проекта нельзя. Изменение клинических фактов или поступление результата делает прежние основания устаревшими.

Семипунктовая форма `synthetic-7-v1` — технический эталон, не утверждённая GAD-7. Только полные ответы 0–3 дают сумму; пропуск, отказ и невозможность заполнения сохраняют неизвестность. Статус источника `synthetic-only` не означает клиническое утверждение. Результаты не создают диагнозы, лекарственные назначения или вывод об отсутствии риска.

Безопасность обрабатывается отдельно: получение в локальную очередь → принятие в работу → оценка врача → подтверждённое действие. Просмотр не меняет этап; откладывание обычной рекомендации не закрывает событие. У заданий сохраняется историческое поле `synthetic-local`, но выданные GAD-7/PHQ-9 уже доступны через пациентский API и Android; исходные ответы возвращаются в серверную карту. [Сквозная проверка](verification/2026-10-27-doctor-integration-polish.md) подтверждает этот поток. Внешняя экстренная доставка и эскалация не подключены.

На API команды `workflow.*` разрешены в Development либо для явно разрешённой синтетической клиники Production, с прежними проверками доступа, CSRF, версии и аудита. Production по умолчанию закрыт; допуск задаётся только серверной конфигурацией Clinical__SyntheticEnabled и Clinical__SyntheticClinicIds. Поле `workflow` добавляется в JSON-карту при первом действии, отдельная SQL-миграция не нужна. Карты текущего контракта без этого поля читаются; это не миграция несовместимого контракта PR #35. Смешанные версии старого клиента и нового API не считаются проверенными. Перед обновлением сохраните копию синтетической БД; откат согласованной сборки выполняйте revert PR с соответствующей копией БД, без ручного удаления истории из JSON.

[Результаты и команды проверки](verification/2026-10-26-synthetic-clinical-flow.md) отделяют выполненные доменные/HTTP-проверки от ожидающих финальных прогонов и клинической валидации.

## Мобильные данные и дистанционная коррекция

В разделе «Уведомления» лента «От пациентов» собирает сообщения, самоотчёты, опросники и отметки о приёме из доступных карт и открывает соответствующий раздел карты. События безопасности остаются отдельно. Отметка «Новое» применяется к непросмотренным самоотчётам; отдельных статусов прочтения врачом для остальных элементов ленты пока нет.

В расписании часовой пояс нового назначения подставляется по устройству врача. При изменении существующего расписания сохраняется его прежнее UTC-смещение. API по-прежнему хранит фиксированное смещение, автоматический переход на летнее время не добавлен. Действие редактирования записи плана называется «Изменить назначение».

В итоге приёма каждая ошибка заполнения открывает нужный раздел и ставит фокус в поле; ошибки согласий открывают форму с нужным назначением документа. Проверки завершения и отдельное подтверждение сохраняются. Технические версии и подробные основания доступны в раскрываемых блоках.

Самоотчёты с телефона доступны в «Наблюдение и шкалы → Дневник»: последняя полученная версия показана сразу, прежние — в «Истории изменений». Просмотр каждой версии отмечается отдельно; прежние сведения о безопасности сохраняются.

При изменении существующего препарата выберите начатый приём. На дистанционном приёме доступны дозировка, обоснование и причина; остальные параметры восстановятся из исходного назначения и будут заблокированы. Если нет допустимого очного основания этого врача, форма объяснит ограничение до отправки. Сервер повторно проверяет решение при сохранении и подтверждении.

[Результаты проверки APK, VPS и Layero](verification/2026-10-27-doctor-integration-polish.md) включают оба опроса, назначения, отметки, самоотчёты и переписку.
