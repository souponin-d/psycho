# Три рабочих пространства администратора

Дата: 20 октября 2026 года. Основание — одобренные пользователем эскизы и поручение реализовать три пространства с совмещением ролей и качественными демо-данными. Владелец — глава разработки; issue ещё не создан. База: 56828af, ветка codex/p10-admin-workspaces. Самостоятельная задача P10; файлы участников #5–#8 не менялись.

## Что реализовано

Одна учебная учётная запись А-01 имеет три роли. Переключатель меняет навигацию, экран и действия, сохраняя последний раздел каждой роли, выполненные задачи, отчётный период, открытый предпросмотр и черновик назначения ролей. Все изменения хранятся в памяти вкладки. Смена набора или перезагрузка начинают новую учебную сессию.

| Пространство            | Разделы                                       | Основной сценарий                                                                                    |
| ----------------------- | --------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Координатор             | Рабочий день, Команда, События                | Открыть организационную задачу, изучить детали, выполнить один раз и увидеть событие и новый счётчик |
| Руководитель            | Обзор, Кабинеты, Отчёт                        | Выбрать подготовленный период, сравнить график и кабинеты, открыть агрегированную сводку             |
| Системный администратор | Сотрудники, Возможности ролей, Журнал доступа | Назначить сотруднику А-02 одну или несколько ролей и увидеть автора и состав ролей до/после          |

Текущий сотрудник и врачебные записи доступны редактору только для просмотра. Пустое назначение не сохраняется; повторное сохранение без изменений не создаёт запись журнала. Переключатель показывает только назначенные текущему сотруднику роли, а прямая ссылка на недоступное пространство предлагает восстановление. Это поведение интерфейса демо, а не серверная авторизация.

Схема данных локальна административному демо. У периодов есть явные календарные границы; проверяются покрытие дней, совпадение общих точек, ссылки на сотрудников и кабинеты, уникальность ID/ролей и суммы. Пропуск показывается разрывом линии и подписью, ноль остаётся числом. Под графиком доступна таблица значений. Ошибка схемы отображается явно вместо нулевой сводки.

## Сценарии данных

Во всех трёх JSON используются synthetic: true, schemaVersion: 1 и фиксированный снимок «20 октября 2026». Обозначения сотрудников, кабинетов и события вымышлены. Это не API DTO.

| Набор           | Координатор                                                       | Руководитель                                                                                     | Системный администратор                                                          |
| --------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| Рабочий день    | 2 задачи, 4 врача, 24 пациента; расписание Д-03 требует уточнения | 31 известный самоотчёт за 7–20 октября, покрытие 13/14 дней; за 14–20 октября — 19, покрытие 7/7 | 6 учётных записей; А-01 совмещает три роли, А-02 начинает с роли координатора    |
| Новое отделение | Нет кабинетов, задач и событий; явные пустые состояния            | Нет дневных данных и кабинетов; отсутствующие данные не объявлены полным периодом                | Только текущая учётная запись; нет сотрудников для редактирования, пустой журнал |
| Длинные подписи | Длинные задачи и обозначения двух кабинетов, 3 пациента           | 14 дневных точек: два значения по 4 и 12 пропусков; сумма 8, покрытие 2/14                       | Длинные имена; А-02 сразу совмещает координатора и руководителя                  |

Суммы normal сохранены: пациенты 8+7+5+4=24, самоотчёты 9+8+8+6=31. Последняя неделя: 6+5+5+3=19. Данные врача Д-01 по-прежнему согласованы с вебом врача. Ни график, ни счётчики не оценивают лечение или работу врача.

## Запуск и воспроизведение

После `npm ci --ignore-scripts` выполнить `npm run dev -- --port 4190`. Открыть сайт, перейти по «Демо администратора». Самостоятельный вход: `npm run dev:admin`; стенд компонентов остаётся в #/examples. Production-вход собирается командой `npm run build`, просмотр — `npm run preview -- --port 4191`; для публикации требуется весь корневой dist.

1. В «Рабочем дне» открыть первую задачу и выполнить её. Остаётся одна открытая задача; в «Событиях» появляется ровно одна запись.
2. Переключить пространство на руководителя: в составе сводки также одна открытая задача. Выбрать 14–20 октября: 19 самоотчётов. Открыть раздел «Отчёт» и предпросмотр.
3. Переключиться на системного администратора, добавить А-02 роль руководителя. До сохранения уйти в другое пространство и вернуться: черновик сохранён. Сохранить, повторить сохранение: в журнале одно изменение с автором А-01.
4. Снять все роли А-02 и сохранить: ошибка, фокус на первом checkbox, журнал не меняется. Текущую учётную запись редактировать нельзя.
5. Вернуться к руководителю: сохранены раздел «Отчёт», выбранная неделя и предпросмотр. Выбрать «Новое отделение», затем исходный набор: действия и черновики сброшены, выбранное пространство сохранено.
6. Проверить длинные подписи, ноль за 9 октября и отсутствие данных за 11 октября в таблице графика; неизвестный hash и #/examples.

## Границы и восстановление

Новых зависимостей, API, БД, миграций и изменений клинических правил нет. Нет настоящей авторизации, постоянного хранения, серверного аудита и экспорта отчётов. Назначение учебной роли не открывает реальные данные. Клинический сценарий и изоляция клиник этим проходом не проверены; нужны серверная реализация и отдельная проверка. Screen reader, Firefox/Safari и проверка с реальными пользователями не выполнялись.

Относится к E03/T04 (интерфейс), T03 (структура демонстрационных данных) из реестра требований. M01 не закрывается: роли врача/пациента и серверные права остаются отдельной задачей. Поддержка совмещения трёх административных ролей основана на уточнении пользователя. Откат — отдельный revert PR; для сброса локальных учебных действий достаточно перезагрузки или смены набора. Публикация и PR этим поручением не запрашивались.
