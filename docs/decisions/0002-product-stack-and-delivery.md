# 0002. Стек продукта и приоритет первой поставки

Дата: 19 октября 2026 года.
Статус: стек и приоритет приняты пользователем; детали архитектуры требуют отдельных решений.

## Основание

В обсуждении 19 октября пользователь согласовал стек для скорейшей разработки веб- и мобильного приложений. Ранее определены три группы: психиатр, пациент и главврач/менеджер; полная экосистема также предусматривает десктоп врача. В репозитории пять контрибьюторов с помощью ИИ. Пользователь самостоятельно делает мобильное приложение, backend и ключевые механизмы. Остальные сдают небольшие PR: 2 — компоненты веба врача; 3 — компоненты дашборда; 4 — общие веб-компоненты; 5 — синтетические данные, страницы примеров и небольшие UI-исправления. CustDev — отдельная командная активность. От остальных не требуется самостоятельно владеть всем стеком.

Обязательные функции определяет [официальный кейс](../official/2026-10-15-case.md). Существующий лендинг остаётся необязательным референсом. Его макеты, имитация состояний и прежний технический замысел не являются реализацией или утверждённой клинической логикой продукта.

## Решение

| Часть                                                 | Выбор                                                                   |
| ----------------------------------------------------- | ----------------------------------------------------------------------- |
| Веб врача и административный дашборд                  | React + TypeScript + Vite                                               |
| Приложение пациента                                   | React Native + Expo development builds; Android и iOS                   |
| Сервер                                                | ASP.NET Core 10, модульный монолит                                      |
| Основная БД                                           | PostgreSQL                                                              |
| Обмен                                                 | REST + OpenAPI; общие клиентские модели и API-клиент                    |
| Организация кода                                      | Один репозиторий; сохраняем npm для JavaScript-инструментов             |
| Десктоп после первоочередных веб-/мобильных сценариев | Tauri с переиспользованием веб-интерфейса врача; Windows, macOS и Linux |

Единое клиническое ядро работает на сервере. Клиническое действие требует подтверждения врача; основание, исходные данные и версии сохраняются. Изоляция клиник и отношение врача с пациентом проверяются сервером.

OCR, модели LLM, конкретные библиотеки UI и тестирования, механизм идентификации, каналы уведомлений и режим локального хранения этим решением не выбираются. Выбор оформляется отдельным обоснованием и проверяется на задачах продукта. Наличие open weights или российского хостинга само по себе не означает допустимость обработки реальных медицинских данных.

## Порядок поставки

Первый приоритет — настоящий сквозной сценарий веб-врача, мобильного пациента и административной отчётности с общим сервером. Полный список требований кейса сохраняется в плане. Десктопная поставка следует после работающей веб-/мобильной цепочки; это изменение порядка, а не удаление целевых платформ.

CustDev проводится параллельно с подготовкой общих контрактов. Его результаты могут изменить сценарии и приоритеты; согласованные изменения фиксируются до реализации зависимых задач.

## Открытые решения

- Первая клиническая популяция, возраст, нозологии, амбулаторный/стационарный режим и исключения.
- Правила и источники терапии, критических состояний, маршрутизации, дежурства и эскалации; клинический проверяющий.
- Российское централизованное или локальное размещение и защищённый доступ пациента из дома. Автономное заполнение анкеты не решает доставку алерта без связи.
- Границы доступа менеджера, аналитика, главврача и технического администратора; название одной группы не даёт одинакового доступа ко всем данным.
- Нагрузка, допустимые задержки, восстановление и бюджет; численные гарантии пока не согласованы.
- Срок первой рабочей версии относительно предзащиты/финала. План не обещает завершение всей экосистемы к несогласованной дате.

## Последствия

Модель разделения работы, общие контракты и последовательность PR описаны в [плане пяти участников](../superpowers/plans/2026-10-19-five-contributor-development.md). Распределение зон принято пользователем; аккаунты ролей 2–5 и календарь назначаются отдельно. [Стартовые issues](../team/backlog.md) фиксируют следующий шаг. Обработка реальных данных не входит в подготовку этого решения.
