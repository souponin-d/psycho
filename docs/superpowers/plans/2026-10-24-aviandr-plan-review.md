# Проверка Авиандра в плане ведения

> **Статус документа:** Исторический план задачи. Поручения, целевые пути, чекбоксы и ограничения описывают исходную постановку, а не состояние текущего main. Сохранён для требований и прослеживаемости; не использовать как инструкцию запуска. [Текущее состояние](../../status.md).

**Цель:** встроить подготовительную проверку Авиандра в существующее назначение, используя контекст карты пациента. Основание — согласованная в чате схема интеграции; требования F02/F03, M03/M07/M08, T05.

**Архитектура:** необязательное поле `aviandrReview` назначения хранит структурированные уточнения врача, снимок контекста карты, результаты и версию источника. Общий JSON-каталог определяет неутверждённые проверки; локальный домен и ASP.NET пересчитывают результаты при сохранении и подтверждении. Клиническая активация отсутствует, обычное подтверждение остаётся решением врача. Свободный текст карты показывается для сверки, но не превращается автоматически в отрицание риска.

**Стек:** существующие React/TypeScript/Vite, ASP.NET Core 10/PostgreSQL; без новых зависимостей и миграций.

## Ограничения и решения

- ОХЛП от 16.07.2026 получена по ссылке с сайта производителя; сверка редакции в ГРЛС и клиническое утверждение ещё не выполнены. Статус всегда `unapproved`.
- Не выдавать «безопасен», «подходит», автоматическое назначение, отмену либо клиническую блокировку. Неутверждённые результаты информационные.
- Сохранить существующие карты без нового поля, существующее подтверждение, неизменяемость завершённых приёмов, конфликты и идемпотентность.
- Не передавать данные пациентов внешним справочникам. Внешняя ссылка открывает только документ.
- Чужую работу над mobile/site и lockfile исходного checkout не менять.

## Задачи

- [x] Модель и домен: тесты неизвестных данных, взаимодействий, противопоказаний, границ дат/единиц и отсутствия клинической активации; затем каталог и локальная оценка. Проверка включает снимок используемого контекста.
- [x] UI: выбор Авиандра в существующей форме, контекст карты, структурированные уточнения, раздельные результаты, сохранение/повторное открытие и сравнение актуальности. Не терять текст при обновлении карты.
- [x] API: строгая валидация входов, серверное вычисление и авторство результата, повторная оценка при подтверждении, совместимый OpenAPI через генератор. Не доверять клиентским результатам и статусу утверждения.
- [x] Приёмка: unit/UI/API проверки, общий check/check:web/check:fixtures, сборка .NET, снимки на desktop/mobile; документ с результатами и ограничениями.

## Особое внимание при проверке

Неизвестное не равно отрицательному ответу; свободный текст и нераспознанные лекарства не дают положительного заключения; новый контекст делает уточнения устаревшими; клиент не может подделать утверждение/результат; назначение другого препарата не наследует проверку Авиандра.
