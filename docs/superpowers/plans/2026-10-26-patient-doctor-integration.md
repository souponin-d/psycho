# Интеграция пациента и врача: план реализации

> **Статус документа:** Исторический план задачи. Поручения, целевые пути, чекбоксы и ограничения описывают исходную постановку, а не состояние текущего main. Сохранён для требований и прослеживаемости; не использовать как инструкцию запуска. [Текущее состояние](../../status.md).

> Выполнять по шагам через superpowers:executing-plans. Основание: утверждённый пользователем план и [issue #52](https://github.com/souponin-d/psycho/issues/52). Android и синтетический прототип; макеты новых интерфейсов требуют утверждения до внедрения.

**Цель:** надёжный обмен данными между мобильным приложением пациента и кабинетом врача через сервер.

**Архитектура:** версионированный пациентский контракт, идентификация и авторизация на сервере, локальная очередь с устойчивыми идентификаторами, независимые серверные записи и подтверждение результата. Демо изолировано. Пациентские события не превращаются в действия врача и не теряют исходные ответы.

**Стек:** React Native / Expo, React / TypeScript, ASP.NET Core, PostgreSQL, REST / OpenAPI. Зависимость интерфейса от PR #51; основа кабинета врача — main после #50.

## Ограничения

- Дистанционно в прототипе разрешена только корректировка дозировки уже назначенного препарата лечащим врачом при зафиксированных условиях очного диагноза, очного назначения и соответствующей консультации. Смена и добавление препарата требуют отдельного очного назначения. Это более узкое продуктовое ограничение, чем текст закона.
- Часть 3 [статьи 36.2 323-ФЗ](https://www.consultant.ru/document/cons_doc_LAW_121895/ccf02734a76e335943ae86f86b319d6035cca374/) и пункты 38–39 [приказа Минздрава № 193н](https://publication.pravo.gov.ru/document/0001202505150033) описывают коррекцию ранее назначенного лечения; необходимо сохранять основание, автора и историю. Клинические правила и активация требуют утверждения врача по AGENTS.md.
- Не отправлять синтетические демофакты после подключения к серверу; не переносить локальную историю автоматически без подтверждённого происхождения и связи с пациентом.
- Контракт меняется вместе с потребителями и проверками; сгенерированный клиент не редактировать вручную. APK выдаётся локально, не публикуется на VPS.

## Шаги

1. Очередь: `src/core/patientOutbox.ts`, `tests/patient-outbox.test.ts`. Сохранять команду и её постоянный ID до отправки; не удалять без подтверждения и успешной записи; переживать рестарт, сетевой сбой и потерю ответа; изолировать записи по серверу и идентичности пациента; последовательный запуск и без дублирования при параллельных вызовах. Подключение в `PatientConnectionProvider.tsx` только после определения безопасной привязки учётной записи, с тестами смены режима и аккаунта.
2. Переписка: изучить `patientChannel.ts`, `contact.tsx`, `PatientJournal.tsx`, существующие команды и состояния доставки. Подготовить до/после для утверждения. После утверждения отобразить историю и отправку через очередь; не выдавать серверное сохранение за прочтение. Проверить пациента и врача через настоящий API.
3. План: согласовать контракт `PlanVersion` и серверных `PlanItem`, версий, слотов, отмен и дат действия. Реализовать ограниченную пациентскую проекцию подтверждённых назначений, синхронизацию и исторические версии; отдельно защитить ограничение дозировки на сервере и в интерфейсе врача. Проверить конфликт и чужую карту, сверить контракт и потребителей.
4. Приём: связать события `DoseEvent` с ID назначения и слота; команда пациента, сохранение исправлений, отображение врачом без подмены источника. Сквозной тест приёма, пропуска, неизвестного состояния и исправления после смены плана.
5. Самоотчёты: явное соответствие `ReportFields` и модели врача; сохранять исходные ответы и версию; передавать события и исправления. Проверить данные пациента, отсутствие утечки между пациентами и вид врача.
6. Опросники: согласовать серверные назначения и версии PHQ-9/GAD-7 с мобильными `QuestionnaireAssignment` и `QuestionnaireEvent`; передавать исходные ответы, дополнительные поля, время и результат только в пределах утверждённых правил. Проверить полный путь назначения, прохождения, сохранения и отображения, а также повтор и отмену.
7. Проверка: `npm run check`, `npm run check:mobile`, `npm run check:web`, `npm run check:fixtures`, API/PostgreSQL integration и Android-сквозные сценарии с синтетическими данными; фиксировать точные результаты. Сборка APK локально. Изменения доставляются через PR в main с независимым review.

## Риски проверки

Смена профиля во время передачи; сервер сохранил команду, но ответ потерян; повреждённая очередь и отказ записи; конфликт версии плана; чужая карта и отозванный доступ; локальное демо рядом с серверной сессией; новое назначение вместо допустимой коррекции дозы; несовпадение версий и источников опросника. Тестировать на соответствующем шаге.
