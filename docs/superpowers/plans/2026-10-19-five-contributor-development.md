# Разработка клинической экосистемы — план пяти контрибьюторов

> **For agentic workers:** Use `superpowers:executing-plans` for the assigned issue only. Respect its allowed files and verification class. Contributors 2–5 must not expand a small task into backend, mobile, security, or clinical-engine implementation.

**Goal:** Ускорить работу главы разработки за счёт четырёх участников, выполняющих небольшие изолированные задачи с простой приёмкой.

**Architecture:** Модульный монолит ASP.NET Core 10 и PostgreSQL обслуживают веб врача, административный веб и мобильное приложение. Глава разработки реализует сервер, мобильное приложение, клинические механизмы и подключение интерфейсов. Остальные участники сдают через PR компоненты веба врача, дашборда, небольшие общие компоненты, синтетические данные, страницы примеров и UI-исправления. CustDev проводится отдельно командой.

**Tech Stack:** React, TypeScript, Vite; React Native, Expo development builds; ASP.NET Core 10; PostgreSQL; REST/OpenAPI. Десктоп Tauri следует после первоочередной веб-/мобильной поставки.

**Spec:** [Официальный кейс](../../official/2026-10-15-case.md), [решение о стеке](../../decisions/0002-product-stack-and-delivery.md), [CONTRIBUTING.md](../../../CONTRIBUTING.md). Основание распределения: пользователь разрабатывает мобильное приложение и ключевые функции сам; остальным нужны быстрые задачи без необходимости владеть всем стеком. Глава разработки — souponin-d; соответствие аккаунтов ролям 2–5 и срок уточняются в [стартовых issues](../../team/backlog.md).

## Global Constraints

- Участник 1 — пользователь, глава разработки. Он владеет всей мобильной разработкой, backend, API, БД, доступом, клинической логикой, интеграциями, CI и поставкой.
- Участники 2–5 не являются самостоятельными full-stack владельцами. Они получают одну небольшую issue с перечисленными файлами, готовыми входами и способом проверки.
- Прямой push в `main` запрещён. Все изменения проходят отдельную ветку, PR, независимое одобрение и обязательные checks; слияние — squash merge.
- «Быстро проверить» означает ограничить риск и область задачи. Изменения доступа, назначений, алертов, хранения и синхронизации требуют полноценных проверок и не передаются как простые задания.
- Продуктовые приложения пока не созданы. Все пути ниже планируемые. Лендинг `site/` — необязательный референс; имитация из демо не является клиническим алгоритмом.
- Используются синтетические данные. Источники, переводы шкал и права использования проверяются до включения в продукт; собранный участником материал не становится действующим правилом автоматически.
- Клинические действия требуют подтверждения врача. Версии источников, исходные факты, авторство и история решений сохраняются на сервере.
- Полный перечень требований кейса сохраняется. Промежуточный интеграционный сценарий не считается полной версией. Десктоп остаётся следующим этапом с Windows/macOS/Linux.

## Review Focus

1. Чужая клиника, несвязанный врач, подменённый идентификатор, отозванный доступ: сервер закрывает карточки, документы, сообщения, отчёты и события. Владелец проверок — 1, задачи P01/P07/P10.
2. Повтор запроса или обработчика после сбоя: один самоотчёт, одно подтверждение и прослеживаемая повторная доставка. Владелец — 1, P04/P05/P08.
3. Неполные/противоречивые сведения, неподтверждённый факт, отсутствующая версия источника: явное состояние недостаточности данных без выдуманного назначения. Владелец — 1 с клиницистом, P02/P05/P06/P09.
4. Одновременное редактирование и устаревшее подтверждение: конфликт версии, сохранение истории и отсутствие автоматической перезаписи лечения. Владелец — 1, P05/P09.
5. Нет сети, врач недоступен, сбой БД: честный статус доставки и проверяемое восстановление; офлайн-анкета не означает доставленный алерт. Владелец — 1, P08/P12/P13.

Мобильное приложение полностью у участника 1. Для компонентов участников 2–4 входы передаются через готовые props, выходы — через callbacks. Компоненты не запрашивают API, не реализуют авторизацию и не хранят медицинские данные. Участник 5 не меняет поведение экрана под видом небольшого визуального исправления.

Для диалогов и полей участник 4 использует подготовленные доступные примитивы: не пишет заново focus trap, обработку фокуса или медицинскую валидацию. Клинически значимые предупреждения и подтверждения остаются у 1.

**Основной вклад каждого участника — полезное изменение в репозитории через PR. CustDev — отдельная командная активность.** Интервью, реестр источников и медицинский разбор не подменяют задачи участников 4/5 в коде. Интервью распределяются отдельно; решения по результатам принимает 1. Клиническое содержание утверждается с клиницистом. Протоколы не содержат идентифицирующих медицинских данных.

## 2. Как выдавать небольшую задачу

До первой issue каждый проходит [чек-лист подготовки своего рабочего места](../../team/local-development-setup.md). В нём разделены уже доступные команды лендинга и будущие команды продуктовых приложений. В P01 глава разработки создаёт изолированный запуск компонентов и Node-проверки для участников 2–5 без .NET, БД и мобильных SDK; серверные/мобильные проверки сохраняются отдельно в CI.

Перед назначением issue глава разработки предоставляет:

1. Один конкретный результат: например, «показать переданный список пациентов», а не «реализовать кабинет врача».
2. Точный список разрешённых файлов, описание входов/выходов и пример результата. Новый участник не проектирует общий контракт.
3. Готовый минимальный запуск или шаблон документа/данных, не требующий настройки всего backend.
4. Короткую проверку: команда, 2–4 наблюдаемых состояния и скриншот/другой артефакт.
5. Запреты, зависимости и назначенного проверяющего.

Одна задача — один компонент, документ или набор примеров. Ориентир размера — результат за одну короткую рабочую сессию; это не обещание времени. Если задача требует нового endpoint, миграции, зависимости, системного разрешения, обработки конфликта или медицинского решения, участник фиксирует вопрос в issue и не расширяет область самостоятельно. Глава разработки выделяет критичную часть себе либо разбивает задание.

При обычной правке ориентир — 1–3 файла и до 150–200 строк вручную написанного кода; это средство ограничения объёма, не жёсткий лимит. В issue указывается класс проверки:

| Класс                               | Какие задачи                                                                           | Достаточная проверка                                                                                                                                                                     |
| ----------------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — материал**                    | Текст, реестр ссылок, синтетический пример по шаблону                                  | Соответствие шаблону, отсутствие реальных данных, формат/ссылки или готовый валидатор; отдельные автотесты не нужны                                                                      |
| **B — представление**               | Отображение и композиция готовых UI-примитивов без запросов и бизнес-логики            | Существующие проверки типов/сборки, просмотр с готовыми данными, пустым/длинным содержимым; для диалога — клавиатура/фокус, для поля — callback. Не дублировать тесты готовых примитивов |
| **C — бизнес-поведение/интеграция** | API, мобильное приложение, вычисления, доступ, клиническое действие, события, хранение | Владелец 1: автоматические проверки нужного поведения, отрицательные случаи и реальная интеграция                                                                                        |

Общие обязательные checks PR остаются для всех классов. Сейчас `npm run check` проверяет документацию и лендинг; глава разработки добавляет проверки приложений по мере их появления. Простые задачи не требуют от участника самостоятельно проектировать тестовую инфраструктуру или разворачивать клинический контур. Если проверки показывают несвязанный сбой, участник сообщает его, а не отключает check.

## 5. Порядок основной разработки

Коды P00–P14 сохранены как идентификаторы крупных результатов; каждый результат делится на небольшие PR. Владелец технической реализации всех P-задач — **1**. H-задачи обозначают ограниченную помощь и не передают ответственность за механизм.

Независимое одобрение и клиническая проверка сохраняются.

CustDev идёт отдельным командным процессом и не закрепляет участника 4 только за исследованиями. Его результаты могут изменить приоритеты по решению 1; принятые изменения фиксируются до затрагивающей их реализации.

Помощь должна снимать работу с главы разработки, поэтому сначала каждый получает одно пробное задание. Следующее выдаётся после принятого PR. Если компонент оказался сложным, задача уменьшается до конкретной разметки/состояния или примера по шаблону; скрыто передавать участнику целое приложение не нужно. При оценке сроков команда не считается пятью полноценными параллельными full-stack разработчиками.

Глава разработки держит одну основную критичную задачу и ограниченную очередь PR на просмотр. Продукт собирается рабочими итерациями; календарь оценивается по его фактическому темпу и принятым результатам остальных. Дата полной версии пока не согласована.

## 8. Работа с ИИ и ревью

Каждому участнику в issue выдаётся точный запрос для ИИ: цель, разрешённые файлы, готовые входные данные, запреты, способ запуска и критерий приёмки. Агент читает `AGENTS.md`, не расширяет задачу и не меняет конфигурацию ради собственного результата. В PR автор сообщает, что проверил лично; отсутствие проверки не маскируется отметкой ИИ.

Для H-задач глава разработки проверяет границы, результат и отсутствие скрытой логики. Для собственных P-задач глава разработки заранее назначает другого контрибьютора для независимого воспроизведения конкретных проверок; тот может пользоваться ИИ, но должен лично проверить свидетельства. Формальный approve без понимания задания недопустим. Если проверяющий не способен оценить критичный пункт, он отмечает это: автоматические проверки и содержательная/техническая проверка остаются необходимыми, а не считаются выполненными по умолчанию.

Клиническое принятие выполняет клиницист и оно не заменяется ни главой разработки как автором кода, ни участником, собравшим ссылки. Командные правила PR и запрет прямого push сохраняются независимо от класса задачи.
