# Кабинет врача на Layero с API на VPS — диагностика и план

> Для исполнителя: применять `superpowers:executing-plans` после поручения реализации. Это диагностика и проект работ; код приложения, настройки Layero и VPS при подготовке документа не менялись.

**Цель:** сохранить основной сайт и `/doctor/` на `https://syncli-main.layero.app/` с автодеплоем из main; направить `/api/*` через небольшой Node.js-прокси Layero на существующий ASP.NET API/VPS. Android обращается к VPS напрямую.

**Архитектура:** статика корневой `dist/` остаётся на edge Layero; отдельная fullstack backend-половина обслуживает только `/api` и проксирует фиксированный HTTPS upstream. БД, авторизация, клиническая логика и данные остаются на VPS. Прокси не хранит общую пользовательскую сессию, cookies или данные карт в памяти/на диске.

**Стек:** Vite/React/TypeScript, Node.js 24 с HTTP/HTTPS-модулями, ASP.NET Core 10, PostgreSQL, Caddy. Покупка домена не требуется.

**Основания:** уточнение пользователя; прочитанный чат «ПРИЛОЖЕНИЕ 2» (`01a175b7-ec25-76f0-b88c-0f9843b4945c`); [контур обмена](../../contracts/mobile-server-web-contour.md), [поставка VPS](../../../deployment/demo/README.md), [отчёт VPS](../../verification/2026-10-26-vps-hackathon.md).

## Диагностика

- Основной сайт Layero отвечает 200 с валидным TLS.
- `/api/health` на Layero сейчас отвечает 200 `text/html`, побайтово совпадающим с главной страницей: 84981 байт. Это статический SPA-fallback, а не ответ API.
- `r1282061.s2590.vm.mydomain.zone` имеет A `176.32.37.10` и AAAA `2a00:b700:3::2c7`. По техническому имени проверка TLS не завершилась успешно; DNS сам по себе не подтверждает HTTPS.
- `https://176.32.37.10/api/health` через существующий CONNECT-туннель отвечает 200 с проверкой TLS. Туннель привязан к IP; отдельная проверка имени через тот же IP с сохранением TLS-имени также завершилась ошибкой handshake. Проверка сертификата не отключалась.
- В связанном чате подтверждены прежний SSH-доступ и опубликованный обмен Android → VPS → врач → Android. Приватные настройки и реквизиты не переносятся в git, frontend bundle или конфигурацию Layero.
- На предыдущем диагностическом проходе новые `/api/terminology/icd10` и `/api/terminology/grls` на VPS вернули 404; опубликованный web-артефакт был старее PR #43. PR #43 уже MERGED. Нужна отдельная проверка/поставка актуального API.
- Web уже использует относительный `/api`, cookie `same-origin`, CSRF, версии карты и устойчивый commandId. Переписывать клиент для прямого cross-origin обращения к VPS не требуется.
- По опубликованной конфигурации VPS работает в Production; новые workflow/support/adherence пока требуют Development. Это отдельный блокер новых клинических функций, не причина менять схему хостинга.

Авторизованное чтение карт и запись сообщений в этом проходе не выполнялись. Живые настройки проекта Layero, его тариф и сетевой доступ из runtime к VPS ещё нужно проверить в отдельном preview.

## Проверенные возможности Layero

[Официальный fullstack-конфиг](https://docs.layero.ru/deploys/layero-json/) описывает `frontend`, `backend` и `apiPrefix`: статика раздаётся файлами, API обслуживает контейнер. Внутри блоков используются короткие ключи `build/output/start/node`; backend runtime нужно согласовать с настройкой проекта. Обычные внешние rewrites в основу решения не закладываются.

[Runtime](https://docs.layero.ru/runtime/overview) поддерживает Node-сервер на `0.0.0.0:$PORT`. [Lifecycle](https://docs.layero.ru/en/runtime/lifecycle) указывает лимит 60 секунд на запрос, cold start и остановку неактивного процесса; [диск эфемерный](https://docs.layero.ru/runtime/stateless/). Данные и фоновые задачи в прокси не размещаются. Кэширование `/api` требует самостоятельной проверки, а не вывода из поведения страниц.

## Порядок реализации

### 1. Подтвердить fullstack-маршрутизацию в preview

Файлы: новый `layero.json`, минимальный backend-процесс в `deployment/layero/`, тест конфигурации поставки.

- [ ] Прочитать текущие настройки существующего проекта, не создавать новый production-сайт и не менять автодеплой main на ручную публикацию.
- [ ] Сохранить сборку всего корневого dist: лендинг, doctor и admin; frontend собирается из корня монорепозитория с существующим lockfile, Node 24.
- [ ] Выделить лёгкий backend без React/Expo/.NET-зависимостей и БД; определить фактическое применение node_web в fullstack-настройке проекта.
- [ ] Проверить в preview, получает ли backend префикс `/api` или путь без него, и направлять upstream путь с одним `/api`.
- [ ] Проверить доступ из Layero runtime к VPS и TLS. Первичный upstream — подтверждённый HTTPS IP; техническое имя использовать только после проверки его сертификата и Caddy-конфигурации.
- [ ] Проверить `/`, `/doctor/`, asset URLs и JSON health без SPA-fallback на `/api`.

### 2. Реализовать ограниченный stateless-прокси

Файлы: `deployment/layero/` с сервером/конфигурацией, тесты прокси; корневой контракт ASP.NET остаётся источником истины.

- [ ] Фиксированный HTTPS upstream из серверной настройки. Нельзя выбирать произвольный хост или URL через query, path или присланный Host.
- [ ] Передавать метод, query, тело, Content-Type, Cookie, X-CSRF-TOKEN, коды ответа и отдельные Set-Cookie без объединения через запятую. Не создавать общий cookie jar между пользователями.
- [ ] Убирать hop-by-hop и недоверенные forwarded-заголовки; upstream Host/TLS-имя соответствуют VPS. Не расширять доверие ASP.NET до произвольных прокси.
- [ ] Сохранять host-only cookies без VPS Domain, Secure/HttpOnly/SameSite и правильное удаление при logout. Нормализовать только необходимые upstream redirects к публичному origin.
- [ ] Явно запрещать кэш API/авторизации; проверить отсутствие edge-cache и утечки ответа между двумя сессиями на самой Layero.
- [ ] Ограничить входные тела согласованно с API (2 МБ), использовать потоковую передачу ответов/PDF без накопления целого тела в памяти.
- [ ] Таймаут upstream меньше лимита платформы; 502/504 возвращать как JSON, не HTML. Не повторять POST автоматически. Повтор инициирует клиент с тем же commandId.
- [ ] Таймаут/индикатор первого клиентского запроса учитывать cold start; не считать короткое пробуждение доказательством потери сессии. Не использовать runtime-таймеры для фоновой синхронизации.
- [ ] Проверить лимит входа: без отдельно подтверждённой передачи IP браузера сервер видит адрес прокси, и пользователи могут делить один rate-limit. Не решать это доверием к клиентскому X-Forwarded-For.

### 3. Согласовать и обновить API на VPS

Файлы: deployment/demo, серверная политика синтетического выполнения, отчёт поставки/версии контракта.

- [ ] Зафиксировать release/API contract ID, резервную копию и откат; обновить API отдельно от Layero, сохранив БД, ключи, сертификаты, пользователей, коды и care relationships.
- [ ] Поставить новые каталоги/манифесты/правила и нужные файлы форм; проверить поиск и сохранение МКБ-10/ГРЛС.
- [ ] Для новых синтетических workflow/support/adherence ввести отдельный явный opt-in с серверным ограничением клиник, сохранив Production и проверки доступа. Не переводить VPS в Development.
- [ ] Подтвердить совместимость старого Android: вход по коду, чтение messages, отправка обращения и повтор commandId продолжают работать напрямую.
- [ ] Подготовить backend до переключения production-web на новые обязательные возможности; при несовместимости показывать понятную ошибку версии, а не запускать локальный режим автоматически.

### 4. Сквозная приёмка и включение автодеплоя

- [ ] Layero: CSRF → login → session → общая карта → команда → reload → logout. Secure cookies должны принадлежать Layero-origin браузера, данные сохраняться на VPS.
- [ ] Android → обращение → тот же пациент в Layero-web → ответ → Android; прежняя история сохранена.
- [ ] Проверить две независимые сессии/клиники, чужую карту, отсутствие CSRF, истечение сессии, конфликт ревизии, потерю ответа, дубликат команды, холодный старт и недоступность VPS.
- [ ] Убедиться, что ни API JSON, ни cookies не кэшируются edge; полные cookies, пароли, тексты сообщений и карт не попадают в логи Node.
- [ ] Подтвердить автодеплой main и полный dist, preview для PR и возврат на предыдущий Layero deploy. Backend откатывается отдельным согласованным релизом.
- [ ] Выполнить npm run check, check:web, check:fixtures, HTTP/Production proxy tests и Chromium на публичном Layero-origin; зафиксировать cold/warm задержки и фактические runtime-лимиты проекта.

## Границы этапа

Новый посредник обеспечивает транспорт существующего REST API и не переносит бизнес-логику или БД на Layero. Полная синхронизация Android-шкал, дневника, слотов приёма и клинического плана остаётся отдельным этапом; `message.patient` её не подменяет. Покупка домена и смена основного адреса продукта в план не входят.

Новая issue/ветка создаются при начале реализации. Этот план не публиковался и не запускал деплой.
