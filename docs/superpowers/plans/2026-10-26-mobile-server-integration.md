# План интеграции Android пациента с кабинетом врача и VPS

**Статус:** порядок работ подтверждён владельцем; контур спроектирован, реализация и публикация не начаты.
**Цель:** общий проверяемый поток пациент → сервер → врач → подтверждённый план → пациент.
**Архитектура:** существующие Expo/SQLite и ASP.NET Core 10/PostgreSQL; один совместимый REST/OpenAPI-контракт. Сервер определяет пациента, клинику и доступ. Демоданные изолированы. iOS исключён.

## Основания и фактическое состояние

Изучены чаты «СЕРВЕР», «ВРАЧ 3», «ПРИЛОЖЕНИЕ»; планы мобильного обновления, врачебных MI-задач и общий backlog A01–A08/A36. Последний отчёт «СЕРВЕР»: VPS подготовлен, PostgreSQL работает, API-служба не установлена, Caddy остановлен, домен/HTTPS приложения не настроены. Кандидат ca0ee6d от 0ae22a1 не включает текущие незавершённые изменения кабинета врача. Повторный read-only SSH 26 октября завершился timeout; состояние VPS в этот момент независимо не подтверждено. Сервер, DNS и маршруты Windows не изменялись.

## Спроектированный контур

[Приложение — сервер — кабинет врача](../../contracts/mobile-server-web-contour.md): ответственность, вход, проекции, версии, очередь, обмен, отказы и приёмка. Эта спецификация уточняет первый этап; остальные этапы сохраняют порядок.

## Первый результат для хакатона

[Уточнённый доступ](../../contracts/hackathon-access.md): Android — только код при каждом новом запуске; врач — форма логина/пароля вместо учебного входа. Код многократный для одной синтетической карты. Сначала проверяются реальные сессии и обмен тестовым сообщением/ответом через PostgreSQL. Полный клинический профиль и расширенная синхронизация сохраняются ниже как последующие этапы.

## Порядок работ

0. **P0 — профиль медицинской защиты.** Целевой контур — клиника в России. До реального пилота выполнить [этап защиты](../../contracts/medical-data-protection.md): паспорт обработки, модель угроз/уровень защищённости, площадка, криптопрофиль, ключи, шифрованные Android/сервер/копии, доступ и аудит. Учесть назначение СППВР, ЭМД/МИС и телемедицинского процесса. Текущий VPS остаётся кандидатом для синтетики; пригодность для реальных данных не подтверждена. Синтетические проверки интеграции можно продолжать, проектируя защиту до фиксации контрактов и хранилищ.
1. **P0 — совместимый контракт и релиз (A36).** Зафиксировать стабильную базу кабинета врача, API и Android 0.4.1, включив проверенные исправления прокси. Согласовать пациентскую проекцию, версии опубликованного плана, самоотчёты, исходные ответы/версии опросников, дозы, исправления и обращения. Проверка: одинаковые примеры проходят клиентские и серверные контрактные тесты.
2. **P0 — общий HTTPS-стенд.** После выбора домена и согласования публикации развернуть совместимый API и кабинет врача на подготовленном VPS, настроить Caddy/systemd, секреты вне сборок, резервирование и проверку восстановления. Проверка: health с БД, вход и HTTPS доступны с Android; откат воспроизводим. Сначала разобрать замечания зависимостей из релизного отчёта.
3. **P0 — вход пациента (A01).** Реальная сессия, согласованный способ приглашения/привязки, отзыв доступа, выход и изоляция кэша/очереди по аккаунтам. Деморежим не отправляет свои факты на сервер. Проверка: чужой пациент/клиника и отозванный доступ недоступны.
4. **P0 — двусторонние данные (A02/A03).** Подтверждённый врачом план поступает на телефон; отчёты, отметки приёма и разрешённые ответы поступают в карту врача с происхождением и временем. Сохранить локальную историю/мир; версии и отмены корректируют напоминания. Очередь SQLite, устойчивый commandId, повторы без дублей, конфликты без молчаливой перезаписи. Проверка: обрыв до/после записи, перезапуск, изменённый план, отказ/пропуски анкеты.
5. **P0 — обращения и ответы (A04).** Связать обращения пациента с врачом и показывать подтверждённые сервером статусы сохранения/доставки/прочтения. Навигатор не выдаёт себя за ответ врача. Проверка: отсутствие адресата, отзыв связи, офлайн, повтор и ответ врача.
6. **P0 — сквозная приёмка и APK.** Синтетический пациент в реальном Android-клиенте отправляет данные на VPS; врач видит их в серверном режиме, публикует изменение, телефон получает его. Проверить обновление поверх 0.4.1, сохранность данных, сессии, фон, отказы сети и напоминания. Выдать APK, запись сценария и результаты. A08 не закрывать без отдельной серверной аналитики A06.

До серверного этапа необходимы доступный SSH, точный домен, разрешение публикации и совместимый контракт. Не требуется ждать всех MI-задач врача. Активация клинических правил и реальные пациентские данные остаются за отдельным утверждением; медицинские пороги не придумываются. Сервер/контракты и публикация проходят установленное PR-ревью; одобрение плана не заменяет независимое одобрение PR.
