# P01a: план реализации оболочек и стенда

Задача: [#4](https://github.com/souponin-d/psycho/issues/4). Владелец: souponin-d. Основание: [проект решения](../specs/2026-10-19-web-foundation-design.md).

Документ описывает будущую реализацию. Пункты ниже не являются свидетельством готовности; текущие статусы задач ведутся в GitHub.

## Общие условия

- Работать в codex/4-web-foundation от актуального origin/main; сохранить существующий лендинг.
- Установка из одного корневого lockfile: Node.js 24, npm ci --ignore-scripts; версии зависимостей точные.
- Два приложения, общий ui-web, встроенные примеры. Только синтетические данные и состояние в памяти.
- Дизайн-скиллы не использовать. Общий стиль взять из демо с проверкой читаемости и клавиатуры.
- Контракты и границы #5–#8 сохранить; приложения, схемы и примитивы готовит глава разработки.
- Общие, веб- и fixture-проверки работают без API/.NET/БД/mobile; обязательные CI jobs не пропускать.
- Изменения передаются PR в main, без локального merge или прямого push в main. Независимую проверку выполняет другой контрибьютор; самопроверка агента её не заменяет.

## 1. Workspace и две запускаемые оболочки

Создать manifests в apps/web-doctor, apps/web-admin и packages/ui-web; общую TypeScript-конфигурацию; Vite-конфигурацию, index.html и src/main.tsx каждого приложения. В корневом package.json добавить workspaces и команды dev:doctor/dev:admin, сохранив текущие scripts лендинга. Корневой package-lock.json обновлять только npm.

Приложения импортируют общий исходный пакет через явные exports. Для повторного подключения React использовать одну совместимую версию React/React DOM; не допускать нескольких копий React. Сборки выводить в отдельные dist приложений.

- [ ] Проверить актуальные совместимые версии выбранных библиотек и зафиксировать их точно.
- [ ] Создать минимальные оболочки с русскими заголовками и отметкой синтетических данных.
- [ ] Проверить npm ci --ignore-scripts, запуск каждого приложения и независимость от сборки ui-web.
- [ ] Проверить, что npm run check продолжает проверять лендинг и документацию.

## 2. Контракты и синтетические данные

Создать tests/fixtures/presentation/normal.json, empty.json и long.json. Создать scripts/check-fixtures.ts с экспортируемой проверкой файла и CLI, проверяющим весь обязательный набор. Ошибки содержат файл и путь поля; CLI завершается ненулевым кодом. Команда check:fixtures запускает тесты валидатора и валидацию реальных наборов.

- [ ] Проверить, что типы данных выводятся из тех же схем, которые использует валидатор.
- [ ] Сохранить минимальные наборы: расширение конкретных JSON-файлов остаётся за #8.

## 3. Общие примитивы и тема

Создать src/primitives/Button.tsx, TextField.tsx, Dialog.tsx и LineChart.tsx внутри ui-web; src/styles/tokens.css, base.css и локальные ресурсы Onest с лицензией. Явные exports разделяют стили, примитивы и контракты.

Dialog экспортирует DialogRoot, DialogTrigger и DialogPanel поверх Radix. Panel обеспечивает обязательный заголовок и кнопку закрытия. Trigger совместим с asChild и передаёт ref. Собственный focus trap не писать. LineChart получает ChartSeries, сохраняет порядок точек и предоставляет SVG вместе с таблицей.

- [ ] Написать проверки связи label/input/hint/error, disabled и callback поля.
- [ ] Написать проверки controlled open, onOpenChange(false), Escape и возврата фокуса диалога в DOM-среде; закрытие и повторное открытие не оставляют старого состояния.
- [ ] Написать проверки пустой, одноточечной и постоянной серии, отрицательных значений, нуля и null; разрыв линии и значения таблицы должны соответствовать входам.
- [ ] Реализовать примитивы и повторить проверки. Новые тесты должны проверять поведение обёртки, а не внутреннюю реализацию Radix.
- [ ] Применить компактное оформление из проекта решения; проверить контраст, видимый фокус, disabled и длинный текст.

## 4. Навигация, примеры и подключения участников

Создать общую небольшую hash-навигацию и оболочку. Доктор использует #/patients и #/examples, администратор — #/summary и #/examples; неизвестный адрес показывает восстановимую ошибку. Создать выделенные страницы примеров:

- apps/web-doctor/src/examples/PatientList.example.tsx;
- apps/web-doctor/src/examples/InfoDialog.example.tsx;
- apps/web-doctor/src/examples/Primitives.example.tsx;
- apps/web-admin/src/examples/DepartmentSummary.example.tsx.

Создать типизированные заготовки PatientListView.tsx, DepartmentSummaryView.tsx и InfoDialogView.tsx в presentation-директориях соответствующих приложений/ui-web. Отмечать в них номера задач; не реализовывать компоненты вместо участников. Готовый стенд примитивов должен демонстрировать реальное поведение без этих компонентов.

Журнал стенда держит последние 20 вызовов callback в памяти. Смена набора или примера сбрасывает журнал и выбранный id. Ошибка данных не маскируется пустым состоянием. Приложения не используют HTTP и localStorage для демонстрационных данных.

- [ ] Проверить начальные/неизвестные hash, прямую ссылку, перезагрузку и Back/Forward.
- [ ] Проверить обновление заголовка/фокуса при навигации.
- [ ] Проверить запись аргумента callback, ограничение журнала и сброс при смене примера/набора.
- [ ] Включить переключатели normal/empty/long и отдельные состояния базового поля/диалога.
- [ ] Убедиться, что для работы #5–#8 достаточно их конкретных файлов и уже зарегистрированных примеров.

## 5. Запуск стенда и CI

Порты 8767/8768, host 127.0.0.1 и strictPort задаются явно. При старте/сбое дочернего процесса возвращать ошибку и завершать второй процесс; при Ctrl+C не оставлять серверы.

Создать корневую конфигурацию Vitest и команды check:web/check:fixtures. check:web включает TypeScript, поведенческие проверки обоих приложений/ui-web и сборки приложений. check:fixtures включает проверки валидатора и JSON-наборов. Добавить отдельные Web checks и Fixture checks для Windows/Ubuntu в .github/workflows/checks.yml, сохранив существующие Repository checks.

- [ ] Проверить запуск dev:examples и доступность обоих адресов.
- [ ] Проверить ошибку занятого порта и завершение второго процесса при сбое первого; повторный запуск не должен находить оставленные процессы.

## Проверка полноты плана

Все критерии #4 сопоставлены шагам: приложения/примеры — 1/4; типы/примитивы/схема — 2/3; команды — 1/5; веб-/fixture-CI — 5; чистая установка — 5; точные входы H-задач — 6; готовые места регистрации — 4. Поведение нулей/null, диалога, hash, журнала и остановки процессов проверяется в том шаге, который вводит соответствующий механизм.

План не утверждает готовность продукта и не заменяет независимое ревью или клиническую проверку будущих функций.
