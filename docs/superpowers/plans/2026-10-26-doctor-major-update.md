# Крупное обновление кабинета врача: исследование и задачи

> **Статус документа:** Исторический план задачи. Поручения, целевые пути, чекбоксы и ограничения описывают исходную постановку, а не состояние текущего main. Сохранён для требований и прослеживаемости; не использовать как инструкцию запуска. [Текущее состояние](../../status.md).

Дата: 26 октября 2026 года. Ветка: `codex/doctor-major-update`, создана от локального `0ae22a1`. Незакоммиченные документы предыдущего разбора сохранены. Основание: [спецификация минимального ввода](../specs/2026-10-26-doctor-minimal-input-design.md) и явное требование пользователя предоставить всю МКБ-10.

> Для исполнителя: это согласуемый перечень результатов и границ будущих issues. Применять `superpowers:executing-plans` только к назначенной задаче после согласования её контрактов и файлов. Статусы и assignees ведутся в GitHub Issues. Этот документ не сообщает о реализации MI01–MI13 и не разрешает клиническую активацию.

**Цель:** кабинет и API на синтетике обрабатывают готовые результаты и изменения пациента; врач подтверждает факты и решения без повторного перепечатывания. Полная российская МКБ-10 обязательна уже в первом обновлении.

**Архитектура:** расширить существующие `PatientRecord`, команды, репозитории, аудит и экраны. Сохранить одинаковую семантику локального домена и API. Единые факты, оценки, рекомендации и решения отображаются общими проекциями; новую независимую копию контекста в каждом разделе не создавать.

**Стек:** существующие React/TypeScript/Vite, ASP.NET Core 10/PostgreSQL, REST/OpenAPI; Node.js 24/npm. Новые библиотеки и реальные серверные подключения этим планом не требуются автоматически.

## 1. Границы текущей работы

- Кабинет врача и серверная логика работают только с синтетическими сведениями. Можно использовать локальный согласованный API-стенд и тестового пациента; отдельную инфраструктуру общей интеграции пользователь предоставит позже.
- Существующие локальный IndexedDB-репозиторий и API-адаптер переиспользуются. Не строить второй демонстрационный движок с другой медицинской семантикой и не переписывать хранение ради нового макета.
- Мобильный UI, настоящая синхронизация телефона, административный веб, лендинг и эксплуатационное развёртывание отложены. A01–A08 остаются в общем списке, но не блокируют подготовку синтетического врачебного сценария. Полная сквозная приёмка M02 при этом не закрывается.
- Общие типы, миграции, доступ, домен и тесты принадлежат главе разработки; клинические эталоны утверждает клиницист. Участники 2–5 могут получить только ограниченные UI/fixture issues по командным правилам.
- Утверждение схемы и явных технических инвариантов не равно утверждению медицинских порогов. Иллюстративный рост GAD-7 из пользовательского текста не включается как медицинское правило по умолчанию.
- Планирование и новые документы не меняют продуктовый код. Перед каждым PR определить точные файлы и требуемые проверки; не редактировать сгенерированный клиент вручную.

## 3. Подтверждённые пробелы

1. В `terminology.ts` ровно 17 учебных записей; в `Domain.cs` отдельно зашиты те же 17 кодов/названий и учебная версия. Остальные коды не только отсутствуют в выдаче, но и отвергаются сервером.
2. `Episode.diagnosis` остаётся строкой, `EpisodeForm` показывает поле «Диагноз / гипотеза». Структурированное требование выполнено для приёма и соматики, но не для всех активных путей.
3. Аллергии и текущие лекарства — общие строки профиля; источники/подтверждения/актуальность каждого отдельного факта не хранятся в требуемой форме. Дата обновления профиля не решает эту задачу.
4. В `PatientRecord` нет единой рекомендации с предложенным жизненным циклом и нет команд принять/изменить/отклонить/отложить её. `CareEvent` и `PlanItem` имеют другие назначения и не заменяют эту сущность.
5. Полный вход ответа пациента не создаёт автоматически врачебную карточку с расчётом, сопоставлением и изменениями отдельных ответов. `measurement.add` требует явно переданные сведения о результате; подготовительный расчёт не закрывает новый поток.
6. Рабочий день показывает расписание, верхний сигнал и последние записи; это пока не полная очередь решений.
7. Приём показывает прошлый контекст, но не собирает пофактную дельту с прошлого контакта и не предлагает короткие решения вместо повторного содержания.
8. `plan.confirm` требует `rationale`/`patientInstructions`, а все переходы события требуют текстовую заметку. Нужно целевое изменение команд обычных рекомендаций с автоматическим основанием; нельзя просто отключить обязательность текста во всём домене.
9. У события нет отдельной модели доставки; безопасность и обычные задачи используют общий список без требуемого полного разделения. Отдельное состояние «безопасность не оценена» по пропуску/отказу не задано в нужном процессе.
10. Проект направления не заполняется из единой рекомендации. Автовыдача разрешённого самоопросника по утверждённому протоколу в новом врачебном потоке отсутствует.

## 4. Полная МКБ-10: приоритет P0

Пользователь явно запретил ограничиваться учебным срезом. MI02 — первый поставляемый результат обновления, включая локальную синтетику. Импорт всей российской МКБ-10 не заменяется МКБ-10-CM другой юрисдикции, таблицей популярных кодов или одной главой.

Целевой первоисточник — [Реестр НСИ Минздрава, OID 1.2.643.5.1.13.13.11.1005](https://nsi.rosminzdrav.ru/dictionaries/1.2.643.5.1.13.13.11.1005). [Официальная страница ТФОМС Татарстана](https://www.fomsrt.ru/infinter/classifiers/fed_nsi/index.php?ELEMENT_ID=1616) указывает этот реестр как место актуальной публикации и отдельно обозначает свои старые выгрузки датами 2020–2021 годов.

На этапе исследования доступный веб-инструмент не получил карточку НСИ, а проверенный адрес ЕСНСИ ответил 403; браузерная загрузка НСИ завершилась таймаутом. **Текущая версия, число записей и полная выгрузка ещё не получены и не проверены.** Их получение — обязательный первый шаг MI02; старую копию нельзя молча объявить актуальной. Ограничение доступа не является основанием сократить каталог до 17 записей или придумать отсутствующие коды.

Паспорт импорта должен фиксировать точный источник/версию/дату, условия использования, число записей, разделы, контрольные суммы и воспроизводимую нормализацию. Для постраничного источника проверяются все страницы и их итог, а не только первая выдача. Клиент и API получают один проверенный набор из общей процедуры подготовки; два вручную поддерживаемых перечня исключаются.

## 5. Новые задачи без дублирования A01–A83

MI01–MI13 — 13 новых самостоятельных результатов. Пересекающиеся медицинские правила и приёмка остаются в A09–A22; они не размножаются в новые задачи. Конкретные файлы ниже — зоны исследования; точные разрешённые файлы назначаются в issue после согласования контракта.

### MI01. Единый реестр клинических фактов

**Приоритет:** P0. **Связи:** A36/A24; разделы 2, 5, 7 спецификации.

Согласовать и реализовать идентичность факта, происхождение, подтверждение, применимость/давность и историю замены. Диагноз, заболевание, лекарство и аллергия не требуют повторного ввода на каждом экране. Исходная цитата/ответ сохраняется после подтверждения врачом; неизвестно отличается от отрицательного ответа.

**Приёмка:** одно уточнение отражается во всех представлениях; подтверждение не теряет происхождение; конфликт/замена оставляют историю и не меняют завершённый снимок; частичное обновление не подтверждает весь профиль. Проверить локальный домен и API. Срок актуальности не задавать произвольной константой.

### MI02. Полная российская МКБ-10 во всех полях

**Приоритет:** P0, первый результат ветки. **Связи:** A36/A49; раздел 10 спецификации.

Получить и проверить полную актуальную исходную выгрузку, подготовить единый версионированный артефакт и заменить обе учебные коллекции. Переиспользовать `TerminologyPicker`; обеспечить полный достижимый поиск по коду/названию с пагинацией/виртуализацией при необходимости. Распространить структурированное представление на диагноз эпизода и все другие активные пути диагноза/соматики; сохранить статусы гипотезы и подтверждения.

**Приёмка:**

1. Состав и число записей сверены с независимыми метаданными/полной исходной выгрузкой, подтверждена обработка всех страниц и разделов.
2. Из каждого опубликованного раздела исходника выбраны контрольные записи, отсутствующие в прежних 17; проверены первые/последние записи выдачи и коды с подрубриками.
3. Поиск по коду, названию, регистру, пробелам и «е/ё» возвращает достижимые результаты; ограничение первых 12 кнопок не скрывает остальные совпадения.
4. Выбор сохраняется в диагнозе приёма, эпизоде и соматике после reload; код/название/версия совпадают в UI, локальном домене и API.
5. API принимает допустимый код вне старого списка и отвергает подмену названия/версии или отсутствующий код. Результаты не определяются оставшимся hardcoded whitelist.
6. Исторические записи старой версии читаются по записанной версии; старый свободный текст не угадывается и не стирается. Нужны согласованные миграция/совместимость и откат, включая локальную синтетику.
7. Поиск доступен без отдельного интеграционного сервера и внешнего подключения при каждом вводе. Полнота каталога не выдаёт врачу дополнительные полномочия подтверждать диагноз.

**Зоны:** `terminology.ts`, `TerminologyPicker.tsx`, `PatientForms.tsx`, `model.ts`, `commands.ts`, `Domain.cs`, процедура подготовки каталога и регрессии контракта/совместимости. Не править generated-клиент руками.

### MI03. Автоматическая карточка новой оценки пациента

**Приоритет:** P0. **Связи:** A20/A24/A36; раздел 6.3.

Определить синтетический вход полного набора ответов и серверный результат: версия/период/роль оценщика, исходные ответы, полнота/отказ, вычисленные значения, исходный и предыдущий сопоставимые результаты, изменения пунктов. Переиспользовать проверенные подготовительные вычисления после утверждения нужного ключа; не переписывать все 18 форм и не превращать черновики в активные измерения автоматически.

**Приёмка:** карточка появляется без ручного ввода суммы/копирования ответов; поддельная сумма клиента не принимается как авторитетная; частичная форма не становится нормальным результатом; разные версии не смешаны; ручной внешний результат явно обозначен исключением. Результат доступен врачу из карты и приёма по одному ID.

### MI04. Единая рекомендация и объяснимое основание

**Приоритет:** P0. **Связи:** A09/A13/A15/A24/A36; разделы 2–3, 8.

Добавить общий объект рекомендации со всеми типами, приоритетом, ограничениями, источником/версией, связанными фактами и предлагаемым действием. Отделить его от события безопасности, элемента плана и факта. Медицинские правила остаются в существующих A-задачах; в MI04 не создавать произвольный клинический движок поверх них.

**Приёмка:** рабочий день, карта, приём, план и очередь используют один ID; повтор на том же основании не дублирует объект; новая версия входов помечает прежнее основание устаревшим и сохраняет решение; объяснение восстанавливается без ручного перепечатывания врачом.

### MI05. Короткое решение врача и условная причина

**Приоритет:** P0. **Зависимости:** MI01/MI04. **Связи:** A14/A16/A22; раздел 4.

Реализовать проверку ключевого факта и принятие/изменение/отклонение/откладывание рекомендации. Причина обязательна при изменении, отклонении или клиническом противоречии. Для обычного принятия безопасного предложения основание записывается из рекомендации без обязательного свободного текста. Не путать этот сценарий с лекарственным назначением или выполнением клинического действия.

**Приёмка:** API проверяет допустимые переходы и актуальность контекста, формирует автора/время и защищает повтор; изменение/отказ без причины отклоняются. Открытие не выполняет действие; подтверждение клинического действия остаётся отдельным. Подтверждённые лекарственные ограничения не ослаблены.

### MI06. Изменения с прошлого контакта и точечное подтверждение

**Приоритет:** P0. **Зависимости:** MI01/MI03. **Связи:** A19/A21/A36; разделы 5, 6.4.

Переиспользовать `PatientContext`/`PatientBrief` и сформировать дельту новых/изменённых/спорных/устаревших фактов относительно последнего контакта. Повторный пациентский ответ «ничего не изменилось» моделировать синтетическим входом; мобильный экран пока не разрабатывать.

**Приёмка:** неизменившиеся подтверждения не просятся заново; изменение лекарства/аллергии не подтверждается молча; явное исправление одного факта не требует заполнить весь анамнез; полная история доступна и исходное происхождение сохранено.

### MI07. Рабочий день как очередь решений

**Приоритет:** P1. **Зависимости:** MI04/MI05/MI11. **Связи:** A10/A29; раздел 6.1.

Расширить существующий `Workday`: пациент, одно предлагаемое действие, приоритет/срок, основание, статус и короткие действия. Расписание сохранить доступным. Статус решения общий с картой; срочный сигнал безопасности не теряется при сортировке/откладывании обычных задач.

**Приёмка:** решение из рабочего дня видно в карте без повторного ввода; очередь не дублирует рекомендацию на каждый экран; проверены пустая выдача, длинные основания, клавиатура и узкая ширина.

### MI08. Клиническая сводка карты

**Приоритет:** P1. **Зависимости:** MI01–MI06/MI11. **Связи:** A75/A78; раздел 6.2.

Развить текущий обзор: структурированные диагнозы/статусы, план, новые данные, рекомендации, безопасность, сопоставимая динамика и требующие проверки сведения. Развёрнутый анамнез и документы оставить в истории, не копировать их в новые обязательные поля.

**Приёмка:** по сводке понятно, что изменилось и какое решение нужно; действие меняет исходный объект, а не текстовую копию; неподтверждённый факт визуально и семантически не становится подтверждённым диагнозом.

### MI09. Приём с минимальным повторным вводом

**Приоритет:** P1. **Зависимости:** MI03/MI05/MI06/MI10/MI11. **Связи:** A29/A76; разделы 6.4, 7.

Начинать с дельты, активных рекомендаций, задач и фактов для проверки. Провести инвентаризацию каждого обязательного поля: новый факт, решение либо исключение. Длинный анамнез сворачивается; ответы/результаты/основания берутся из исходных объектов.

**Приёмка:** обычный повторный сценарий не требует перепечатать старые данные; новое врачебное заключение не создаётся под видом автоматически скопированного текста; безопасность оценивается отдельно. Сохранены черновик, конфликт версий, явное завершение и неизменяемый снимок.

### MI10. План из принятых решений

**Приоритет:** P0. **Зависимости:** MI04/MI05. **Связи:** A03/A14/A21; раздел 6.5.

Преобразовывать принятое решение в связанную задачу, шкалу/дату, контакт, рекомендацию пациенту или мониторинг. Основание и источник переносятся автоматически. Операция идемпотентна и проверяет актуальность данных. Лекарственное назначение остаётся отдельным существующим защищённым процессом.

**Приёмка:** повтор не даёт две задачи; отказ/откладывание не создают подтверждённое назначение; клиническое действие требует своего подтверждения. Результат виден в карте и приёме без нового ввода; пациентская публикация в будущий клиент пока не заявляется доставленной.

### MI11. Отдельная безопасность, доставка и незавершённая оценка

**Приоритет:** P0. **Зависимости:** MI01/MI03/MI04. **Связи:** A09–A12/A22; раздел 6.6.

Сохранить существующую последовательность клинической обработки и аудит. Добавить различие обычной задачи и события безопасности, факты доставки и явное состояние «безопасность не оценена» при отказе/пропуске. Согласовать совместимую модель с API и локальным доменом; реальную экстренную доставку/эскалацию не дублировать вместо A10/A11.

**Приёмка:** просмотр/доставка не выполняют действие; неполный ответ не даёт ложного отсутствия риска; отложенная обычная рекомендация не скрывает открытое событие безопасности; закрытие и медицинский исход требуют соответствующего решения и основания.

### MI12. Проект направления или обследования из рекомендации

**Приоритет:** P1, после первого контура. **Зависимости:** MI01/MI04/MI05; A13/A14 и клиническое утверждение. **Раздел:** 6.7.

Расширить существующие `Referral`/`Referrals`, предзаполняя адресата, причину, факты, источник, уже проведённые исследования и недостающие данные. Для обследования определить связь с существующим видом элемента плана; не создавать второй независимый список без необходимости.

**Приёмка:** врач может изменить/отклонить проект; принятие предложения не равно выдаче направления; отдельное подтверждение сохраняет автора и первоначальные основания. До этого этапа ручные направления продолжают работать.

### MI13. Выдача разрешённого самоопросника по протоколу

**Приоритет:** P1. **Зависимости:** MI03/MI04/MI10; A20 и утверждённые условия ветки. **Раздел:** 8.

Добавить выдачу только разрешённого пациентского самоопросника в пределах заранее утверждённого протокола. Сохранять правило/версию, дату, основание и назначенный слот; не повторять выдачу при каждом открытии карты. На текущем этапе исполнение пациентом моделируется тем же синтетическим контрактом.

**Приёмка:** неподтверждённая версия и врачебная шкала не выдаются автоматически пациенту; изменение условий не переписывает прежний результат; выдача не меняет лекарственную схему и не создаёт неподтверждённый клинический маршрут.

## 8. Порядок реализации в этой ветке

1. **MI02 — вся МКБ-10:** сначала получить/проверить полную выгрузку, затем единый набор, все активные поля, UI/API и сохранность старых записей. Небольшой поднабор не принимается даже для синтетики.
2. **MI01 и A36 — факты и контракт:** происхождение/подтверждение/актуальность, версии и совместимость. Подготовить расширения рекомендаций/результатов до экранов.
3. **MI03 и A20 — одна оценка:** синтетические ответы, утверждённая форма, расчёт и карточка без переноса врачом.
4. **MI04/MI05/MI10 — рекомендация, решение, план:** единая сущность, короткие действия, автоматическое основание, отдельное подтверждение клинического действия и защита повторов.
5. **MI11 и A09/A12 — безопасность:** отдельный тип/незавершённая оценка, утверждённый сценарий опасных признаков, порядок обработки; доставку/эскалацию продолжить в A10/A11 по согласованному каналу.
6. **MI06–MI09 — рабочие экраны:** дельта, очередь, сводка и приём используют готовые сущности; сохранить прежний визуальный язык и рабочую историю.
7. **A13/A14 и MI13 — первая утверждённая ветка:** объяснимый маршрут и разрешённая анкета. Конкретную ГТР/GAD-7 ветку подтверждает клиницист; пример пользователя не активирует правило.
8. **A19/A21/A22/A29 — приёмка:** полный синтетический врачебный процесс, проверка отсутствия ручного переноса, опасных состояний, полного каталога и измерение действий.
9. **После базовой приёмки:** MI12, новые лекарственные механизмы A15–A18 и расширенная батарея. Настоящая интеграция пациента — отдельный этап после готовности пользовательского сервера.

## 9. Проверки и передача

До реализации зафиксировать согласованные технические контракты и медицинские эталоны; для каждого результата выделить обозримую issue/PR. Не включать все 13 задач одним непросматриваемым изменением только из-за общей ветки крупного обновления.

Для изменений модели/логики использовать `npm run check:web`, `npm run check:mobile` только при затрагивании общего мобильного потребителя, `npm run check:fixtures` при изменении соответствующих fixtures, сборку/API/UI-проверки врача по [runbook](../../doctor-workspace-runbook.md), а также обязательный `npm run check`. Историческая несовместимая БД не используется как новый тестовый стенд без согласованной миграции.

Синтетическая приёмка должна воспроизвести: новый пациентский результат → карточка → подтверждение спорного факта → единая рекомендация → решение → связанная задача/план → аудит. Отдельно пройти неполный/отказной ответ, изменение основания между просмотром и подтверждением, повтор команды, закрытие/возврат, чужой доступ и безопасность. Полный МКБ-10 проверяется независимо от числа пациентов в fixtures.

На этапе исследования `npm run check:web` прошёл: 32 файла, 200 тестов, контракт, парсер, TypeScript и обе web-сборки. Это базовая проверка прежней реализации; она не доказывает выполнение MI01–MI13. Предупреждение крупных экспортных чанков администратора сохраняется.

Сейчас изменяются только документы планирования. Продуктовые схемы, API, каталоги, клинические правила и интерфейсы ещё не изменены. Для будущих схем отдельно нужны совместимость, миграция/откат и независимое ревью; активация клинических веток требует записанного утверждения врача.
