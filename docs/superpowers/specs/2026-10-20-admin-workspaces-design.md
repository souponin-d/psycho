# Три рабочих пространства администратора

Основание: 20 октября 2026 пользователь одобрил интерактивные эскизы и поручил реализовать их в административном вебе с качественными демо-данными. Один сотрудник может совмещать роли. Это самостоятельная задача главы разработки P10; issue ещё не создан. Файлы компонента задачи #6 не затрагиваются.

## Результат

- Одна учебная учётная запись А-01 имеет три пространства. Переключатель меняет навигацию, заголовок и доступные действия. Последний раздел каждой роли, задачи, период отчёта, предпросмотр и черновик ролей сохраняются при переключении.
- Координатор: очередь организационных задач, раскрытие деталей, однократное выполнение, обновление счётчика и журнала; расписание команды и события.
- Руководитель: показатели, график с подписями и разрывами при отсутствии данных, выбор подготовленного периода, согласованная таблица кабинетов и предпросмотр агрегированного отчёта. Открытые задачи отражают действия координатора.
- Системный администратор: синтетические сотрудники, выбор сотрудника, редактирование одной или нескольких рабочих ролей, явное сохранение и журнал с автором, прежними и новыми ролями. Учётная запись А-01 показана только для чтения; врачебные записи не редактируются этим демонстрационным редактором.
- normal: 4 врача, 24 пациента, 31 известный самоотчёт за 7–20 октября, отсутствие данных за 11 октября; за 14–20 октября 19 самоотчётов. Две организационные задачи, сотрудники с одной и несколькими ролями. empty: новая команда без кабинетов, задач, событий и дневных данных; текущая учётная запись сохраняется. long: длинные подписи, два равных дневных значения и 12 дней без данных, несколько рабочих ролей.
- Смена набора полностью сбрасывает учебную сессию, сохраняя выбранную доступную роль. Перезагрузка сбрасывает действия. Роли из данных определяют доступные варианты переключателя, но не являются авторизацией.

## Границы

React/TypeScript/Vite и существующая тема Onest/зелёный/бумажный фон. Без новых зависимостей, API, localStorage, backend, клинических правил, реальных прав, рассылок и экспорта файлов. Журнал демо не является серверным аудитом. Назначения, диагнозы и клинические действия отсутствуют. Пользовательский путь не ведёт в незавершённый стенд; #/examples остаётся доступен напрямую и через вторичную ссылку для разработки.

Общая оболочка врача, контракты presentation, примитивы и закреплённые файлы участников 2–5 сохраняются. Основной UI администратора получает собственную оболочку, используя общие стили и Button. Схема демо расширяется совместно с её JSON-потребителями; это не API DTO.

## Приёмка

Поведенческие проверки переключения/сохранения/сброса, идемпотентного выполнения задачи, согласованности периода и отчёта, редактирования ролей без пустого назначения, изоляции исходных fixtures и повреждённых наборов. Схема проверяет ссылки, уникальные роли/ID, суммы, границы дат, полноту периодов, совпадение общих дней и присутствие текущего сотрудника. Знаменатель покрытия определяется календарными границами, поэтому потерянный день с нулём не делает сводку полной. Общие check/check:web/check:fixtures; браузер normal/empty/long × три роли, клавиатура и ширины 375/768/1280. Скриншоты и фактические результаты записываются отдельно.
