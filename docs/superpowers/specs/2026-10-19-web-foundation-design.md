# P01a: оболочки веб-приложений и стенд компонентов

Дата: 19 октября 2026 года. Задача: [#4](https://github.com/souponin-d/psycho/issues/4). Владелец: souponin-d.

Статус: вариант 2 выбран пользователем; ниже предложены технические решения для его реализации. Приложения и описанные команды пока не созданы.

## 1. Назначение и границы

После принятия P01a каждый участник с Git, Node.js 24 и npm устанавливает зависимости из корня, запускает свой пример и выполняет проверки без API, .NET, Docker, БД и мобильных SDK. Врачебный и административный интерфейсы имеют рабочую оболочку и места подключения будущих компонентов.

Пользователь выбрал функциональность с базовым оформлением из текущего демо. Отдельная разработка дизайн-системы не требуется. Дизайн-скиллы не используются; решения принимаются непосредственно по требованиям и исходникам сайта.

В эту задачу входят структура workspace, два веб-приложения, базовые UI-примитивы, контракты представления, минимальные синтетические данные, стенд, проверки и документация. Backend, mobile, авторизация, хранение, клинические решения, сообщения, алерты и расчёт административных показателей относятся к следующим задачам.

Компоненты H2a/H3a/H4a и расширение данных H5a сохраняются за исполнителями #5–#8. P01a подготавливает их подключения и минимальные заготовки, явно обозначенные в интерфейсе как незавершённые. Заготовки не изображают готовые список пациентов, сводку или информационный диалог.

## 2. Структура и зависимости

Один npm workspace и один корневой package-lock.json. В workspaces входят apps/web-doctor, apps/web-admin и packages/ui-web. Лендинг site сохраняет существующие команды и сборку.

| Область                          | Ответственность                                                      |
| -------------------------------- | -------------------------------------------------------------------- |
| apps/web-doctor/src/app          | Оболочка врача, навигация, подключение примеров                      |
| apps/web-doctor/src/presentation | Только компоненты врача и заготовка PatientListView                  |
| apps/web-doctor/src/examples     | Готовые страницы примеров врача и общих примитивов                   |
| apps/web-admin/src/app           | Оболочка администратора, навигация, подключение примеров             |
| apps/web-admin/src/presentation  | Только компоненты администратора и заготовка DepartmentSummaryView   |
| apps/web-admin/src/examples      | Примеры административных компонентов                                 |
| packages/ui-web/src/primitives   | Кнопка, поле, части диалога, примитив графика                        |
| packages/ui-web/src/presentation | Заготовка InfoDialogView для #7                                      |
| packages/ui-web/src/contracts    | Схемы данных и типы представления                                    |
| packages/ui-web/src/styles       | Общие CSS-переменные, базовые стили и локальный Onest с лицензией    |
| tests/fixtures/presentation      | Минимальные JSON-наборы normal, empty, long для дальнейшей работы #8 |
| scripts                          | Запуск двух серверов примеров и проверка JSON-наборов                |

Приложения зависят от ui-web; ui-web не импортирует приложения. Общий пакет предоставляет исходные TypeScript-модули через явные exports, без отдельной предварительной сборки и без публикации в npm. Контракты представления не являются будущими DTO API.

Предлагаемый набор библиотек: React/React DOM, TypeScript и React-плагин Vite; Radix Dialog для механики модального окна; Zod для единой схемы данных и выводимых из неё типов; Vitest, Testing Library, user-event и jsdom для проверок поведения. Версии и совместимость фиксируются при реализации точными значениями в manifests и lockfile. Существующий Vite сохраняется, если проверка совместимости не выявит конкретного препятствия.

Оформление — обычный CSS для общей темы и CSS Modules для локальных компонентов. Глобальный менеджер состояния, библиотека маршрутизации, Storybook, Tailwind, библиотека графиков и система сборки монорепозитория в P01a не добавляются.

## 3. Оболочки и навигация

Оба приложения имеют название, заметную подпись «Среда разработки · синтетические данные», навигацию и основную рабочую область. Врач видит разделы «Пациенты» и «Примеры»; администратор — «Сводка» и «Примеры».

Используется небольшая общая навигация по hash: #/patients и #/examples у врача, #/summary и #/examples у администратора. Корневой адрес открывает основной раздел своего приложения. Неизвестный hash показывает сообщение с рабочей ссылкой на основной раздел. Прямое открытие ссылки, перезагрузка и кнопки браузера «Назад/Вперёд» сохраняют выбранный раздел. При смене раздела обновляется заголовок документа; фокус переводится на заголовок основной области при пользовательской навигации.

В разделе врача расположены место списка и область выбранного пациента. До реализации #5 видна подпись о заготовке; после подключения callback показывает только выбранный синтетический идентификатор. Карточка пациента, медицинская история и загрузка данных не моделируются.

В административном разделе подготовлено место сводки и графика. Показатели приходят готовыми строками, серии — готовыми числами. Формулы и медицинская интерпретация отсутствуют.

## 4. Стенд примеров

Примеры находятся внутри двух приложений. Команда dev:examples запускает оба сервера и печатает прямые адреса их разделов #/examples. Отдельного третьего приложения нет.

Врачебный стенд содержит примеры списка пациентов, общих кнопки/поля, базового диалога и будущего InfoDialogView. Административный — сводки и примитива графика. Список примеров регистрирует глава разработки; участник редактирует уже существующий файл своего примера, не меняя маршрутизацию или общий реестр.

Для примеров данных доступны режимы «Обычные», «Пустые», «Длинные подписи». Базовый диалог можно открыть, закрыть и повторно открыть; для поля доступны enabled, disabled, подсказка и переданная ошибка. Контролируемые значения хранятся только в памяти страницы.

Панель действий показывает имя callback и его аргумент. Последние 20 действий сохраняются в памяти, новые добавляются в конец, старые удаляются; кнопка «Очистить» сбрасывает журнал. Смена примера или набора данных очищает журнал и выбранный идентификатор. Это диагностическая панель разработчика, не аудит клинических действий.

Ошибка чтения/валидации набора отображается как ошибка примера с именем файла и путём поля; приложение не подменяет её пустым набором. На этапе сборки ошибочный JSON или несоответствие схеме останавливают проверку.

Серверы слушают только 127.0.0.1: врач — порт 8767, администратор — 8768. Порты фиксированы со strictPort; занятый порт даёт явную ошибку. Переопределение возможно через документированный аргумент отдельной команды запуска. dev:examples использует фиксированные порты и завершает оба дочерних процесса при Ctrl+C или ошибке любого сервера. Скрипт использует Node child_process без shell-команд и работает в Windows и Linux.

## 5. Контракты для H-задач

Имена ниже закрепляются как выходные контракты P01a. Точные imports и примеры будут внесены в #5–#8 после реализации и проверки.

| Контракт                   | Содержимое                                                                                                  |
| -------------------------- | ----------------------------------------------------------------------------------------------------------- |
| PatientRow                 | id: string, displayName: string, secondaryText: string                                                      |
| PatientListViewProps       | rows: readonly PatientRow[], onSelect(id: string): void                                                     |
| SummaryItem                | id: string, label: string, value: string или null, caption?: string                                         |
| SeriesPoint                | id: string, label: string, value: number или null                                                           |
| ChartSeries                | label: string, points: readonly SeriesPoint[]                                                               |
| DepartmentSummaryViewProps | items: readonly SummaryItem[], series: ChartSeries                                                          |
| InfoDialogViewProps        | open: boolean, title: string, children: ReactNode, trigger: ReactElement, onOpenChange(open: boolean): void |

trigger — необходимое дополнение минимального контракта #7: он передаётся в готовый DialogTrigger через asChild, чтобы механикой открытия и возврата фокуса управлял Radix. Кнопка trigger — один доступный элемент, принимающий ref и стандартные обработчики. Участник #7 компонует предоставленные части диалога; собственную механику фокуса не пишет.

Порядок входных массивов сохраняется. Строка value показывается как передана; null означает «Нет данных», строка «0» остаётся нулевым значением. Сами компоненты не форматируют дозировки, не присваивают статусы риска и не вычисляют показатели.

В P01a создаются типизированные заготовки с теми же именами экспортов. Они принимают props, показывают подпись «Компонент будет реализован в задаче #…» и не выполняют работу исполнителя. Стенд общих примитивов работает полностью и независимо от этих заготовок.

## 6. Примитивы

Button использует настоящий button с type="button" по умолчанию, доступным текстом, disabled и видимым фокусом. TextField связывает label, input, hint и error идентификаторами; передаёт value/onChange, disabled и aria-invalid. Он отображает полученную ошибку, но не выполняет бизнес-валидацию.

Диалог предоставляется частями DialogRoot, DialogTrigger и DialogPanel с обязательным заголовком. DialogPanel включает доступную кнопку «Закрыть», portal и overlay. Escape, удержание фокуса, блокировка фона и возврат фокуса обеспечиваются библиотекой. При длинном содержимом прокручивается тело; заголовок и закрытие остаются доступными. Нажатие на overlay закрывает информационный диалог. Проверка закрытия контролируемого окна включает получение onOpenChange(false) и обновление open владельцем.

Примитив LineChart принимает готовую ChartSeries, рисует SVG и предоставляет таблицу с теми же подписями и значениями. Он не считает клиническую динамику. null создаёт разрыв линии и отображается как «Нет данных» в таблице; 0 рисуется как число. Пустая серия показывает пустое состояние, одна точка — маркер, равные числа не вызывают деление на ноль. Геометрия поддерживает конечные отрицательные значения без обрезания; числовой смысл остаётся у поставщика данных. Упорядочивание идёт по входному массиву. Цвет не является единственным носителем информации.

## 7. Данные и валидатор

Каждый файл normal.json, empty.json и long.json имеет корень: schemaVersion: 1; scenario: normal, empty или long; patients: PatientRow[]; department: { items: SummaryItem[], series: ChartSeries }. Объекты строгие: неизвестные поля и неподдерживаемая версия отклоняются.

Схемы находятся в ui-web/contracts; типы данных выводятся из Zod-схем. Props с функциями и ReactNode задаются TypeScript-типами поверх этих типов. Валидатор использует ту же схему, а не её вторую копию.

Идентификаторы непустые, начинаются с demo- и уникальны внутри соответствующего массива. Подписи непустые; secondaryText может быть пустой строкой. Числа конечные; value графика допускает null. В одном наборе scenario соответствует имени файла. Валидатор проверяет все три обязательных файла и завершает процесс ненулевым кодом при отсутствии файла, неверном JSON, нарушении схемы или дублировании идентификатора. Вывод содержит имя файла и путь поля.

Для начала достаточно нескольких записей «Учебный пациент 01», «Учебный пациент 02» и нейтральных показателей. long содержит длинные подписи; normal включает строку «0», отсутствующее значение и ряд с нулём/пропуском; empty — пустые массивы. Эти данные подготавливает глава разработки для запуска. Участник #8 расширяет наборы по выданной схеме в конкретных JSON-файлах. Наличие правильной схемы само по себе не доказывает вымышленность данных: это проверяется просмотром PR. Диагнозы, дозировки, пороги и медицинские эталоны в наборах не задаются.

## 8. Базовое оформление

Onest с лицензией копируется в общий UI-пакет; приложения не импортируют CSS или JavaScript лендинга. Базовые цвета взяты из site/styles.css: фон #fafbf7, текст #1c2924, границы #dfe5dc, зелёный #355e4a, светло-зелёный #c6eba8, лавандовый #e6dff0. Цвет второстепенного текста подбирается с проверкой контраста, даже если для этого потребуется затемнить исходный #707a72.

Тема оформляется небольшим набором CSS-переменных: цвета по назначению, шрифт, размеры текста, интервалы, скругления и фокус. Основной текст 15–16 px; шаг интервалов 4 px; скругления поля/кнопки 6 px, панели 10 px, диалога 14 px. Зелёный выделяет активное действие и навигацию, лавандовый используется умеренно для контекста примеров.

На широком экране навигация и рабочая область расположены рядом; при ширине меньше 768 px навигация становится верхним блоком с переносом ссылок. Внешние отступы 16 px на узких экранах и 24 px на широких. Основные элементы управления не меньше 44 px по высоте. На ширинах 360, 768 и 1280 px нет горизонтального скролла страницы; длинные подписи переносятся. Широкая таблица при необходимости прокручивается внутри своего контейнера.

Текст доступен с контрастом не ниже 4.5:1 для обычного текста; интерактивные границы и фокус различимы. Есть ссылка пропуска навигации, семантические nav/main и заголовки. Анимация ограничена необязательными переходами hover/focus до 150 ms и отключается при prefers-reduced-motion. Декоративных графиков, hero-секций и рекламных блоков в оболочках нет.

## 9. Команды и проверки

Все новые команды ниже планируются; сейчас работают только существующие проверки лендинга и документации.

| Команда из корня        | Результат после реализации                                                  |
| ----------------------- | --------------------------------------------------------------------------- |
| npm ci --ignore-scripts | Установка всех workspace-зависимостей из одного lockfile                    |
| npm run dev:doctor      | Веб врача на 127.0.0.1:8767                                                 |
| npm run dev:admin       | Административный веб на 127.0.0.1:8768                                      |
| npm run dev:examples    | Оба сервера и прямые ссылки на #/examples                                   |
| npm run check           | Существующие общие проверки документации и лендинга                         |
| npm run check:fixtures  | Проверки схем/ошибок валидатора и всех JSON-наборов                         |
| npm run check:web       | Типы обоих приложений и ui-web, проверки поведения, сборки обоих приложений |

Сборки приложений выводятся отдельно в apps/web-doctor/dist и apps/web-admin/dist; сборка лендинга продолжает использовать корневой dist. Общий check не начинает требовать серверные или мобильные инструменты.

Автоматические проверки покрывают конкретные риски: сохранение раздела при навигации, журнал callback, связи label/error, disabled-поле, управляемый диалог, Escape/возврат фокуса в тестовой среде, пустой/одиночный/плоский график, ноль и null, неверный JSON, неизвестное поле, отсутствующий файл и повторяющийся id. Отдельно проверяется завершение dev:examples при ошибке дочернего процесса. Тесты статической разметки заготовок не требуются.

В реальном браузере дополнительно проверяются Tab/Shift+Tab в диалоге, Escape, возврат на trigger, длинное содержимое, изменение масштаба и три ширины экрана. DOM-тест не считается полной проверкой браузерного фокуса.

В CI сохраняются существующие Repository checks на Ubuntu и Windows; добавляются отдельные Web checks и Fixture checks на обеих ОС. Каждая job устанавливает зависимости с npm ci --ignore-scripts; проверки не пропускаются по изменённым путям. Серверные и мобильные jobs появятся с соответствующими приложениями.

Чистая проверка выполняется в отдельной копии/checkout без node_modules и с новым npm ci --ignore-scripts. В записи перечисляются реальные команды и доступность инструментов; успешный запуск на машине с установленным .NET сам по себе не доказывает его отсутствие в требованиях. Доказательство автономности — отдельные Node-only jobs и отсутствие вызовов серверных/мобильных инструментов.

## 10. Передача команде и готовность

Перед снятием блокировки с #5–#8 souponin-d добавляет в каждую issue точные файлы, imports, URL примера, наборы данных, callbacks и команды проверки. Для #7 публикуется дополненный контракт trigger. Для #8 перечисляются только normal.json, empty.json и long.json. Изменение общей конфигурации/реестра примеров исполнителю не требуется.

Зависимость сначала принимается через PR в main; затем участники создают свои ветки от актуального main. После готовности входов и завершённой #3 H-задачи переводятся в ready. До этого они остаются blocked.

README и ролевая инструкция получают фактически проверенные команды. Удалённая по решению пользователя задача #2 исключается из указателя; завершение #3 отражается с указанием подтверждения пользователя. Организационные правила отдельных веток, PR, независимого ревью и squash merge сохраняются.

Для приёмки #4 требуются результаты общих/web/fixture-проверок, CI, свидетельство чистой установки, скриншоты двух оболочек и стенда, запись клавиатурной проверки диалога и обновлённые входы H-задач. Скриншоты показывают UI, но не подтверждают работу клинического продукта.

## 11. Зафиксированные решения и свобода реализации

Пользователь выбрал вариант 2, приоритет функциональности, базовый стиль текущего демо и самостоятельную работу без дизайн-скиллов. Технические решения автора документа: npm workspaces, встроенные галереи, hash-навигация, общий исходный UI-пакет, Radix Dialog, Zod, SVG-график и Node-скрипт запуска двух серверов.

Реализатор выбирает точные совместимые версии, имена приватных вспомогательных функций и разбиение CSS-файлов. Он не меняет закреплённые контракты, области задач участников или критерии готовности без отдельного согласования. Вопросов о клинических алгоритмах для реализации P01a нет: они находятся вне её границ.
