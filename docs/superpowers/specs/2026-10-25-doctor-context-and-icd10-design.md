# Контекст пациента, два статуса и каталог МКБ-10

Основание: пользовательское решение от 25.10.2026 о перестройке учебного
кабинета врача. Учебные данные можно заменить целиком; обратная миграция
демонстрационных записей не требуется. До реализации нужна отдельная приёмка
клинического содержания и источника терминологии.

## Цель

Сделать запись приёма короче и однозначнее:

- в контексте пациента хранить **жалобы** и **анамнез заболевания**;
- во время приёма оставить два самостоятельных повествовательных поля:
  **психический статус** и **соматический статус**;
- выбирать диагноз в заключении, а соматические заболевания в контексте,
  только из поискового каталога МКБ-10;
- не связывать планируемый приём с эпизодом наблюдения.

Каталог не принимает клинических решений: поиск и выбор кода не подтверждают
диагноз, не выбирают лечение и не меняют полномочия врача.

## Источник кодов и его версия

Единственный планируемый первичный источник — указанный пользователем паспорт
НСИ с OID `1.2.643.5.1.13.13.11.1005`:

<https://nsi.rosminzdrav.ru/dictionaries/1.2.643.5.1.13.13.11.1005/passport/latest>.

При проектировании 25.10.2026 страница не открылась через обычную проверку
TLS: браузер и `curl` сообщили о недоверенной цепочке сертификата. Поэтому в
репозиторий не добавляется ни угаданный набор кодов, ни незафиксированная
версия справочника.

Перед импортом владелец каталога передаёт выгрузку из НСИ (JSON, XML или CSV)
либо исправляет доступность паспорта. Импорт фиксирует:

- OID, название, номер/дату версии и URL паспорта;
- дату загрузки, формат, SHA-256 исходной выгрузки и число записей;
- для каждой записи как минимум `code`, русское `title`, признак
  действительности и родительский код, если он есть.

Данные каталога — отдельная версионируемая поставка. Повторный импорт создаёт
новую версию, а не меняет подпись уже выбранного в карте кода.

## Модель

### Контекст пациента

Вместо хранения жалоб и анамнеза в первом приёме `PatientRecord` получает
`clinicalContext`:

```ts
interface NarrativeValue {
  text: string;
  provenance: Provenance;
  updatedAt: string;
  author: string;
}

interface PatientClinicalContext {
  complaints: NarrativeValue;
  illnessHistory: NarrativeValue;
  somaticConditions: TerminologySelection[];
}
```

Пустое значение означает «сведения не внесены», а не отрицание симптома или
заболевания. Изменение значения создаёт новую версию записи в существующем
механизме optimistic concurrency; для рабочей серверной реализации также
сохраняется аудит автора и времени.

`Profile.conditions: string` удаляется. Жалобы и история из `EncounterNotes`
также удаляются; первичный приём показывает их как контекст пациента, но не
создаёт копию в записи приёма.

### Приём

`EncounterNotes` больше не содержит дробные поля `onset`, `functioning`,
`sleep`, `mentalState`, `physicalState`, `mania`, `psychosis` и
`somaticCauses`. Вместо них остаются:

```ts
interface EncounterNotes {
  mentalStatus: string;
  somaticStatus: string;
  substances: string;
  medicationReview: string;
  adverseEffects: string;
  adherence: string;
  suicidalThoughts: string;
  intentAndPlan: string;
  pastAttempts: string;
  meansAccess: string;
  protectiveFactors: string;
  safetyConclusion: string;
  safetyAction: string;
  differential: string;
  conclusion: string;
  recommendations: string;
  patientPreference: string;
}
```

В одной записи психический и соматический статусы не объединяются: выбранное
пользователем разделение сохраняет отдельные авторские описания. Сведения о
веществах, терапии, нежелательных явлениях, приверженности, безопасности и
дифференциальном контексте остаются отдельными, потому что пользователь не
поручал их удалить или объединить.

Диагноз перестаёт быть текстовым `notes.diagnosis`. Заключение содержит
`diagnoses: DiagnosisSelection[]`; элемент включает выбранный код, его
зафиксированное название, статус «рабочая гипотеза» или «подтверждён», а также
версию терминологии. Решение о подтверждении по-прежнему проходит действующую
проверку полномочий, а не определяется выбором кода.

```ts
interface TerminologySelection {
  system: "ICD-10-RU";
  sourceOid: string;
  sourceVersion: string;
  code: string;
  title: string;
}

interface DiagnosisSelection extends TerminologySelection {
  status: "hypothesis" | "confirmed";
}
```

Для ранее выбранной записи отображается сохранённый `code + title`, даже если
в более новой версии каталога её статус изменился. Новая запись выбирается
только из актуальной версии, помеченной в конфигурации.

### Эпизод и запись на приём

`Visit.episodeId` удаляется из модели, валидаторов, API-контракта и формы
«Запланировать приём». Эпизоды могут остаться отдельным информационным
артефактом, но не являются обязательным контейнером приёма и не участвуют в
создании слота. Свободный текст диагноза эпизода не служит вторым источником
истины для заключения: при сохранении эпизодов его нужно заменить ссылкой на
`DiagnosisSelection[]` либо явно убрать после отдельного решения о назначении
эпизодов в новой модели.

## Интерфейс

1. В «Профиль и контекст пациента» добавить раздел «Контекст пациента» с
   полями «Жалобы» и «Анамнез заболевания», а также поиском и списком выбранных
   «Соматических заболеваний (МКБ-10)».
2. В первом шаге приёма вместо редактируемых жалоб и анамнеза показать краткую
   ссылку на контекст пациента. Редактирование открывает форму контекста, а не
   создаёт дубликат.
3. В шаге оценки показывать только «Психический статус» и «Соматический
   статус» для заменяемой группы полей.
4. В заключении поле «Диагноз / рабочая гипотеза» заменить комбобоксом поиска
   по коду и названию, с выбранными тегами и статусом каждого диагноза.
5. В окне планирования оставить причину обращения, дату, формат и длительность;
   селектор эпизода убрать. «Отмена» остаётся, как уже согласовано.

Поиск должен работать с клавиатуры, показывать код и название, не позволять
сохранить произвольный текст как код и сообщать о пустой выдаче. Для большого
каталога результаты фильтруются локально по нормализованным коду и названию;
виртуализация или серверный поиск выбираются только после измерения размера
утверждённой выгрузки.

## Контракт, хранение и учебные данные

- Описание OpenAPI меняется сначала; `api.generated.ts` регенерируется штатной
  командой, вручную не правится.
- Сервер и автономный адаптер принимают только структуру `TerminologySelection`,
  проверяют принадлежность к доступной версии справочника и сохраняют
  снимок выбранного названия.
- Синтетические записи заменяются на schema v2. Старое локальное демо-хранилище
  не мигрируется: при его обнаружении интерфейс предлагает явный сброс учебной
  сессии и объясняет причину. Настоящие данные так не обрабатываются.
- Поиск использует поставляемый снимок каталога и не отправляет текст жалоб,
  анамнеза или другого контекста во внешний НСИ.

## Проверка и границы активации

Автоматические проверки покрывают: выбор по коду и части названия, отсутствие
произвольного кода, сохранение снимка названия/версии, отдельные психический и
соматический статусы, отсутствие `episodeId` в записи и невозможность старого
контракта, а также сброс устаревшего учебного хранилища.

Дополнительно запускаются `npm run check`, `npm run check:web` и связанные
серверные/контрактные проверки. Для UI фиксируются desktop и keyboard-сценарии
поиска, пустая выдача и длинное название.

Это изменение не активирует клинические правила, автоматическую диагностику,
назначения, разграничение доступа или обработку реальных персональных и
медицинских данных. Перед использованием за пределами учебного контура нужны
проверяемая выгрузка НСИ, независимый review общего контракта и клиническое
подтверждение содержания.
