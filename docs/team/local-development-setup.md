# Подготовка к разработке и локальным проверкам

Дата сверки: 29 октября 2026 года. Распределение соответствует [плану пяти участников](../superpowers/plans/2026-10-19-five-contributor-development.md). Пользователь — участник 1; участники 2–5 делают небольшие задачи в репозитории и сдают их через PR. Текущие назначения и зависимости проверяются в GitHub Issues.

**В репозитории есть веб врача и администратора, стенды компонентов, мобильное приложение React Native / Expo и ASP.NET Core API.** Для сервера подготовлены локальные скрипты и конфигурация учебного VPS; общей Docker Compose конфигурации нет. Используются синтетические данные. Проверка приложений не означает клинической готовности. [Точные входы первых задач участников](web-components.md).

## 2. Общий чек-лист для всех пяти участников

- [ ] Установить [Git](https://git-scm.com/downloads) и проверить `git --version`.
- [ ] Получить приглашение в GitHub-репозиторий, принять его и настроить свой HTTPS- или SSH-доступ. Пользоваться личным аккаунтом; общий токен команды не нужен.
- [ ] Настроить своё авторство Git. Значения `git config user.name` и `git config user.email` в клоне должны соответствовать участнику, а не ИИ или другому человеку. Можно использовать GitHub noreply email.
- [ ] Установить [Node.js](https://nodejs.org/en/download) именно ветки **24.x** вместе с npm. Версия закреплена в `.node-version` и `package.json`; `.npmrc` отклоняет несовместимую основную версию.
- [ ] Открыть терминал заново и проверить `node --version` и `npm --version`. Ожидается `v24.*`; отдельную произвольную версию npm глобально не устанавливать.
- [ ] Установить редактор/настроить свой инструмент ИИ. Открывать корень клона, чтобы агент видел `AGENTS.md`, `CONTRIBUTING.md` и назначенную issue.
- [ ] Подготовить браузер: Chrome или Edge достаточно для первого запуска. Уметь открыть DevTools, посмотреть консоль, Network, переключить ширину окна и сделать скриншот.
- [ ] Склонировать репозиторий, установить зависимости и пройти текущую проверку по разделу 3.
- [ ] Получить одну issue с разрешёнными файлами, примером результата и командой проверки. Без неё не создавать собственный каркас или менять стек.

React, TypeScript, Vite, библиотеки UI и инструменты тестирования устанавливаются **из репозитория** вместе с его зависимостями. Не устанавливать их глобально и не создавать новый проект через `create-*` для своей небольшой задачи. Обновление lockfile или зависимостей не входит в обычное компонентное задание.

## 3. Что можно запустить уже сейчас

Клонировать по адресу из **GitHub → Code**. В примере замени `REPOSITORY_URL` реальным адресом, а `YOUR_LOGIN` — своим логином; команды выполняются из выбранной рабочей папки:

```sh
git clone REPOSITORY_URL Psycho
cd Psycho
git fetch origin
git switch -c chore/setup-YOUR_LOGIN origin/main
npm ci --ignore-scripts
npm run check
```

Это пример для **нового клона**. В существующем рабочем каталоге сначала проверить `git status --short` и `git branch --show-current`; не повторять создание ветки поверх незавершённой работы. Новую задачу начинать от актуального `origin/main` после проверки её зависимостей. Прямой push в `main` запрещён. Агентские ветки используют `codex/<issue>-<topic>`.

`npm ci --ignore-scripts` остаётся принятой установкой, включая текущий мобильный workspace. Нативные шаги выполняет глава разработки по [инструкции приложения](../../apps/mobile-patient/README.md); участник не убирает флаг самовольно ради устранения ошибки. При изменении зависимостей необходимые lifecycle-скрипты проверяются отдельно.

Запуск существующего лендинга:

```sh
npm run dev -- --port 8765
```

Открыть адрес, напечатанный Vite, обычно `http://127.0.0.1:8765/`. Если порт занят, выбрать свободный. Остановка — `Ctrl+C`.

Доступные проверки:

| Команда                  | Что действительно проверяет сейчас                                                                  |
| ------------------------ | --------------------------------------------------------------------------------------------------- |
| `npm run check`          | Формат, локальные Markdown-ссылки, синтаксис JavaScript лендинга и общую сборку сайта с веб-входами |
| `npm run format:check`   | Формат поддерживаемых файлов                                                                        |
| `npm run docs:check`     | Локальные ссылки и якоря Markdown                                                                   |
| `npm run site:check`     | Синтаксис `site/app.js`                                                                             |
| `npm run build`          | Сайт и подключённые приложения врача/администратора в корневом `dist/`                              |
| `npm run check:web`      | Контракт и формы врача, типы, web/tools-тесты, сборки обоих веб-приложений                          |
| `npm run check:fixtures` | Fixture-тесты и валидатор синтетических наборов JSON                                                |
| `npm run check:mobile`   | Типы, ESLint и Node-тесты мобильного кода; без Android SDK                                          |

На Windows, если PowerShell блокирует `npm.ps1`, можно использовать `npm.cmd`, например `npm.cmd run check`. Для этого не нужно отключать системную политику исполнения. При смене версии Node сначала заново открыть терминал и проверить, какой `node` доступен в PATH.

**Лендинг не является экраном примеров React-компонентов.** Для компонентов запустить `npm run dev:examples`: примеры врача — `http://127.0.0.1:8767/#/examples`, администратора — `http://127.0.0.1:8768/#/examples`. Ctrl+C завершает оба сервера. Есть отдельные dev:doctor и dev:admin; например, `npm run dev:doctor -- --port 8770` меняет порт одного приложения. Занятые порты не переключаются автоматически. Наличие стенда не снимает блокировку задачи в GitHub автоматически.

## 4. Участник 1 — backend, мобильное приложение и интеграция

Базовый набор из раздела 2 плюс следующие инструменты.

### Сервер и БД

- [ ] Установить **.NET 10 SDK**, не только Runtime: [инструкция Microsoft](https://learn.microsoft.com/en-us/dotnet/core/install/). Проверить `dotnet --list-sdks`: должна присутствовать версия `10.0.*`.
- [ ] Если для отдельной задачи выбран Docker, установить его и проверить `docker version`. Для локальных скриптов API Docker не требуется; контейнер PostgreSQL в CI не делает Docker обязательным на каждом рабочем месте.
- [ ] Подготовить PostgreSQL 17+ и локальный учебный кластер по [руководству врача](../doctor-workspace-runbook.md). Общей `infra/compose.yaml` нет; локальный Windows-скрипт использует установленные утилиты PostgreSQL. Не ставить несколько серверов на один порт. DBeaver или pgAdmin необязательны.
- [ ] Настроить синтетические учётные записи и источники по тому же руководству. Конфигурация VPS описана в [учебной поставке](../../deployment/demo/README.md), Node-прокси — в [Layero](../../deployment/layero/README.md). Локальные пароли и серверные настройки не добавляются в Git.

### Android

- [ ] Установить [Android Studio](https://developer.android.com/studio), Android SDK, Platform-Tools (`adb`), Command-line Tools и Emulator через SDK Manager.
- [ ] Подготовить JDK и Android SDK по [README мобильного приложения](../../apps/mobile-patient/README.md). В workspace уже выбраны Expo SDK 55 и React Native 0.83; номера SDK/Build-Tools не выбирать независимо от проекта.
- [ ] Настроить `JAVA_HOME`, `ANDROID_HOME` и PATH по реальным путям своей установки. Проверить `java -version` и `adb version`; создать и запустить AVD либо подключить Android-устройство с USB debugging и подтвердить доступ компьютеру.
- [ ] Проверить `adb devices`: выбранное устройство/эмулятор доступно. Эмулятор не обязателен при наличии подготовленного телефона, но для локальной нативной сборки Android инструменты SDK/JDK всё равно нужны.

### iOS

- [ ] Для локальной сборки и iOS Simulator нужен **Mac** с Xcode, Command Line Tools и установленной платформой/симулятором iOS; установить CocoaPods. Проверки на Mac: `xcodebuild -version` и `pod --version`. Требования описаны в [руководстве React Native](https://reactnative.dev/docs/set-up-your-environment).
- [ ] На Windows/Linux локальная сборка iOS и запуск iOS Simulator недоступны. Если основной компьютер Windows, заранее обеспечить Mac или согласованный удалённый процесс сборки; подготовленный development build можно тестировать на физическом iPhone. Это не делает сборку локальной на Windows.
- [ ] Для физического iPhone отдельно проверить настройку подписи и способ установки; публикация в App Store — отдельный процесс и не нужна участникам 2–5.

### Команды существующих приложений

API расположен в `apps/doctor-api/`. После подготовки .NET 10, PostgreSQL и конфигурации по [руководству врача](../doctor-workspace-runbook.md), из корня:

```sh
npm run build:doctor:api
npm run dev:doctor:api
```

Из отдельного терминала в корне, после выполнения требований [мобильного README](../../apps/mobile-patient/README.md):

```sh
npm run android --workspace @psycho/mobile-patient
```

На Mac, для iOS:

```sh
npm run ios --workspace @psycho/mobile-patient
```

Metro запускается из корня через `npm run dev:mobile`. Для повторной работы с установленным development build:

```sh
npm run start --workspace @psycho/mobile-patient -- --dev-client
```

Нативные сборки и повторная сборка после изменения нативных зависимостей описаны в [руководстве Expo](https://docs.expo.dev/guides/local-app-development/). Expo Go не заменяет проверку принятого development build. Глобальные `expo-cli` и `react-native-cli` не требуются.

Для настоящего телефона `localhost` — сам телефон. На Android Emulator адрес хоста обычно `10.0.2.2`; физическому устройству нужен доступный адрес компьютера в тестовой сети и согласованные настройки сервера/сертификатов. [Сеть Android Emulator](https://developer.android.com/studio/run/emulator-networking). Не отключать проверку сертификатов в продуктовом коде ради локального запуска. В локальном тесте использовать только вымышленные данные.

Rust, Tauri и платформенные desktop build tools относятся к следующему этапу. Их установка пока не нужна для первоочередных веб-/мобильных задач.

## 5. Участник 2 — компоненты веба врача

**Его часть стека:** React + TypeScript + Vite. **Установка:** только общий набор раздела 2; React/TS/Vite приходят из зависимостей клона. .NET, Docker, PostgreSQL и мобильные SDK не нужны.

- [ ] Получить назначенную issue, готовые типы, пример компонента и точный список файлов `apps/web-doctor/src/presentation/` в актуальном main.
- [ ] Запустить выданный веб-каркас или экран примеров на синтетических данных без API/БД.
- [ ] Выполнить назначенные проверки типов/сборки; просмотреть обычный, пустой и длинный список/хронологию, проверить callback.
- [ ] Приложить скриншот и результат команды к PR. Не исправлять настройку backend и не добавлять запросы API для запуска своего компонента.

Готовность: компонент можно просмотреть и проверить отдельно от серверной среды командами dev:doctor/dev:examples и check:web. Точный файл и пример #5 перечислены в [передаче каркаса](web-components.md#5-список-пациентов).

## 6. Участник 3 — компоненты административного дашборда

**Его часть стека:** React + TypeScript + Vite и уже выбранные в проекте компоненты таблиц/графиков. **Установка:** общий набор; свою графическую библиотеку не устанавливать. Серверные и мобильные инструменты не нужны.

- [ ] Получить назначенную issue, готовые числа/серии, типы фильтров и разрешённые файлы `apps/web-admin/src/presentation/`.
- [ ] Запустить дашборд/экран примеров без API и БД.
- [ ] Проверить сборку/типы, нули и отсутствие данных, длинные подписи, выбранный/сброшенный фильтр и callbacks.
- [ ] Приложить результат и скриншот к PR; не добавлять расчёт медицинских показателей, SQL или загрузку отчёта.

Готовность: показаны переданные значения; самостоятельно рассчитанной аналитики нет. Для #6 использовать dev:admin/dev:examples и check:web; [точные входы](web-components.md#6-сводка-отделения). Изменение панели фильтров требует отдельной задачи.

## 7. Участник 4 — небольшие общие веб-компоненты

**Его часть стека:** React + TypeScript и подготовленные главой разработки UI-примитивы. **Установка:** общий набор. Отдельный сервер, мобильные SDK или новая библиотека компонентов не нужны.

- [ ] Получить готовый примитив диалога/поля, шаблон, экран примеров и конкретные файлы `packages/ui-web/src/presentation/`.
- [ ] Запустить экран примеров без backend.
- [ ] Проверить сборку/типы; для диалога — открытие/закрытие, Escape и возврат фокуса; для поля — подпись, disabled, ошибка и callback; для состояния данных — загрузку/пустоту/ошибку.
- [ ] Передать PR со скриншотами/короткой записью; не писать собственный focus trap, бизнес-валидацию, HTTP-запросы или клиническое подтверждение.

Готовность: небольшая обёртка работает на уже подготовленном фундаменте. Если примитива ещё нет, его создаёт участник 1 до назначения зависимой задачи.

## 8. Участник 5 — синтетические данные, страницы примеров и UI-исправления

**Его часть стека:** JSON и, для страниц примеров, React + TypeScript + Vite. **Установка:** тот же общий набор; Python, PostgreSQL и инструменты BI не требуются.

- [ ] Получить схему/образец данных, подготовленный экран примеров и разрешённые файлы конкретной issue.
- [ ] Для данных выполнить npm run check:fixtures: проверяются структура, версия и идентификаторы по общей схеме, а также normal.json, empty.json и long.json. Это схема представления, не продуктовая клиническая модель.
- [ ] Для страницы примеров запустить каркас, показать обычное/пустое/длинное содержимое без реальных данных; проверить типы/сборку.
- [ ] Для UI-исправления воспроизвести одно замечание, проверить результат и приложить до/после; не менять поведение, общую схему, зависимости или маршрутизацию.

Готовность: данные подходят к выданной схеме, пример открывается в подготовленном каркасе, исправление видно и проверено. От участника не требуется разворачивать клиническую БД или создавать собственный playground.

## 9. Команды существующих приложений и CI

Веб-, fixture- и мобильные Node-проверки реализованы и включены в отдельные jobs Windows/Ubuntu. API проверяется отдельной Ubuntu job с .NET и PostgreSQL. Эти серверные зависимости не нужны для автономных H-компонентов. Таблица описывает существующие команды, а не утверждает, что они прошли в конкретном PR; фактические результаты CI проверяются в GitHub.

| Команда                        | Назначение                                                | Состояние                                         |
| ------------------------------ | --------------------------------------------------------- | ------------------------------------------------- |
| `npm run dev:doctor`           | Веб врача на синтетических данных для задач 2             | Реализована в P01a                                |
| `npm run dev:admin`            | Дашборд на готовых данных для задач 3                     | Реализована в P01a                                |
| `npm run dev:examples`         | Изолированные примеры для 2/3/4/5, без backend/БД         | Реализована в P01a                                |
| `npm run check:web`            | Типы, проверки и сборка веб-/общих UI-модулей без .NET/БД | Реализована; отдельная CI job                     |
| `npm run check:fixtures`       | Валидация синтетических данных по согласованной схеме     | Реализована; отдельная CI job                     |
| `npm run check:doctor:api`     | Проверки подготовленного API-стенда; .NET/PostgreSQL      | Реализована; настройка в руководстве врача        |
| `npm run check:doctor:policy`  | Проверка клинической политики серверного стенда           | Реализована; требуется подготовленный стенд       |
| `npm run check:doctor:ui`      | Браузерные проверки врача                                 | Реализована; требуется подготовленный стенд       |
| `npm run check:doctor:restore` | Проверка сохранения и восстановления                      | Реализована; требуется подготовленный стенд       |
| `npm run check:mobile`         | Типы, ESLint и Node-тесты мобильного кода без Android SDK | Реализована; отдельная CI job, не нативная сборка |
| `npm run check:layero`         | Тесты Node-прокси и структуры поставки                    | Реализована; без удалённого развёртывания         |

- Реальные версии зависимостей закреплены в manifest/lockfile, .NET SDK — в `global.json`, версия PostgreSQL для CI — в workflow API. Изменения версий согласовывает глава разработки; требования нативной сборки находятся в инструкции мобильного workspace.
- Дать каждому участнику один воспроизводимый пример и понятную ошибку, если каркас ещё не готов. Не заставлять запускать API ради просмотра списка или поля.
- Общие Node-проверки и веб-проверки участников 2–5 должны запускаться без установки .NET/мобильных SDK. Серверные и мобильные проверки выполняются отдельными командами и обязательными CI jobs. Это не разрешает пропускать обязательные checks PR.
- Проверить команды на чистой тестовой среде до объявления готовности. Установка `npm ci --ignore-scripts` и нативные шаги мобильной сборки имеют разные задачи; результат Node-проверок не подтверждает Android/iOS-сборку.

## 10. Как сообщить о готовности рабочего места

В issue подготовки или назначенной задаче указать: роль 1–5, ОС, `git --version`, `node --version`, `npm --version`, результат текущего `npm run check`. Для 1 дополнительно — доступность .NET SDK/PostgreSQL/Android и способ проверки iOS. Для 2–5 — какой экран примеров запущен и какая ролевая проверка прошла.

Если часть недоступна, написать точный блокер: например, «Android эмулятор запускается, для iOS нет Mac» или «не выдан контракт зависимой задачи». Не отмечать чужие рабочие места проверенными по своему запуску; локальные проверки продукта не подтверждаются одним запуском лендинга.
