# Подготовка мобильного клиента к patient API

26 октября 2026 года. Это граница подготовки, а не отчёт о подключении телефона к серверу. Владелец API, мобильного кода, доступа и хранения — глава разработки. Нужные контрактные изменения согласуются до реализации; клинические определения утверждает клиницист.

## Что уже существует в репозитории

Источник — [OpenAPI](doctor.openapi.json), операции `patientSession`, `patientRecord`, `patientCommand`, и [серверные маршруты](../../apps/doctor-api/Program.cs). Общие и сгенерированные контракты этим пакетом не изменяются.

| Операция                     | Текущий контракт                                                                                              | Мобильная подготовка                                                                                                     |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| GET `/api/patient/session`   | `actor`, `csrfToken`; cookie-сессия                                                                           | Reader возвращает проверенную внешнюю оболочку; неизвестные поля actor не используются как клиентское разрешение         |
| GET `/api/patient/record`    | `patientId`, `name`, массивы `plan`, `reports`, `messages`                                                    | Reader проверяет внешнюю оболочку; элементы остаются unknown до согласования полной мобильной проекции                   |
| POST `/api/patient/commands` | `commandId`, `mutation`; только `report.add`, `message.patient`, `message.received`; заголовок `X-CSRF-TOKEN` | Не реализовано и не активировано: требуется согласовать смысл исходных мобильных фактов, версий и подтверждения доставки |

`createPatientReader` в [patientGateway.ts](../../apps/mobile-patient/src/core/patientGateway.ts) принимает явный HTTPS origin и внедряемый request port. До явного вызова запросов нет. В штатных providers/экранах reader не импортируется: локальные записи не отправляются автоматически. Отказы 401/403/409 и неизвестный ответ не заменяются учебными данными; серверные тексты и содержимое ответа не попадают в пользовательские сообщения/логи. Для localhost/127.0.0.1/::1/Android emulator 10.0.2.2 HTTP требует отдельного `allowLocalHttp`; это не production-режим.

## Решения перед настоящим подключением

1. Адрес доступного с телефона синтетического стенда, TLS и разрешённый способ входа пациента. Наличие cookie API не подтверждает нативный вход, срок сессии, refresh, выход и отзыв. Секреты и credentials не помещаются в `EXPO_PUBLIC_*`.
2. Формальная пациентская проекция плана: серверный массив `PlanItem` и локальный `PlanVersion` с medication/slots/reportFields/tests различаются. Нужно согласовать дату действия, идентификаторы, отмену, обязательность и версии; автоматически брать первый medication нельзя.
3. Самоотчёт: локальный `ReportFields` включает карту ощущений, сон, тревогу, функционирование и переносимость. Нельзя молча превратить их в серверные clinical scores или потерять исходные ответы/версию формы. Модель хранения опросников и пациентская приватная проекция согласуются отдельно.
4. Отметки доз, исправления, назначения опросников, исходные ответы и обращения о переносимости не имеют полной отдельной семантики в текущем наборе разрешённых mutations. Их не отправляют как произвольный message или report для обхода контракта.
5. Устойчивые `commandId`, серверное время получения, происхождение, конфликт версии и повтор после потери ответа должны быть одинаковыми у клиента/API. В этом пакете серверная outbox и автоматические повторы не включаются.
6. Изоляция реального аккаунта от деморежима, защищённый локальный кэш, судьба черновиков/неотправленных команд при выходе и отзыв care relationship. Сервер определяет patient/clinic; поле, введённое пациентом, не выдаёт доступ.
7. Понятные состояния локального сохранения, серверного получения, доставки и прочтения. «Сохранено» не заменяется на «Доставлено» ради удаления оговорок.

После согласования этих решений выделяются A36 → A01 → A02/A03/A04. Не требуется ждать всех врачебных MI-задач, но нужен принятый контракт конкретной операции. Проверки reader с подставленным transport доказывают только поведение клиента, а не настоящую интеграцию.

## Обязательная проверка будущего подключения

На утверждённом стенде: вход, чужой пациент/клиника, отозванная сессия/связь, потеря ответа после записи, повтор без дублей, изменённый план, возврат из фона, выход со старой очередью и отсутствие отправки демофактов. Реальные пациенты требуют отдельно утверждённого контура; этот документ не разрешает такую эксплуатацию.
