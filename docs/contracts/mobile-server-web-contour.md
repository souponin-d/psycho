# Контур Android пациента — сервер — кабинет врача

26 октября 2026 года. Проектирование по поручению владельца. Порядок этапов интеграции подтверждён; этот документ фиксирует технические границы перед кодом. Исходная реализация — Android 0.4.1 и существующий doctor API; последние врачебные изменения согласуются в общем контракте.

Первый целевой контур уточнён владельцем: клиника в России. [Профиль защиты медицинских данных](medical-data-protection.md) добавляет обязательное шифрование каналов, локального и серверного хранения, копий и управление ключами. До реального пилота определяются модель угроз, уровень защищённости, инфраструктура и применимость сертифицированных средств. Приведённая ниже схема одного VPS описывает синтетический стенд, а не готовую медицинскую площадку.

## 1. Общая схема

Android и браузер врача обращаются по HTTPS к одному origin. Caddy выдаёт web-сборку и передаёт /api в существующий ASP.NET Core API. Только API обращается к PostgreSQL. Мобильный и врачебный интерфейсы получают разные разрешённые проекции одной серверной карты.

Не добавляем отдельный мобильный backend, прямую связь телефона с браузером, доступ клиентов к PostgreSQL или брокер сообщений. Первый контур использует существующий модульный монолит и REST/OpenAPI.

## 2. Ответственность и данные

| Участник      | Ответственность                                                                                                                                                                              |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Android       | Ввод исходных ответов/отметок, локальные черновики, SQLite-очередь, кэш разрешённого плана, нативные напоминания, интерфейс и игровой мир.                                                   |
| API           | Проверка сессии/связи/клиники на каждом запросе, валидация команд, версии, повторы, время получения, публикация плана и аудит. Клинические вычисления только по утверждённым версиям правил. |
| PostgreSQL    | Общая карта, опубликованные планы и история версий, исходные факты/ответы, обращения, квитанции команд и аудит. Запись факта и квитанции атомарна.                                           |
| Врачебный web | Чтение серверной карты, оценка, решение врача, явное подтверждение/изменение/отмена назначения, ответы пациенту. Локальное учебное рабочее место не считается подключённым кабинетом.        |

План, доступ и серверные подтверждения авторитетны на сервере. Черновик пациента остаётся локальным до принятия команды сервером. Клинические черновики врача не видны пациенту. Проекция пациента формируется явным списком разрешённых полей: без внутреннего заключения, рекомендаций врачу и скрытых результатов опросников. Игровой мир сохраняется отдельно от клинических фактов; существующие локальные сведения не загружаются автоматически в карту.

## 3. Вход

Для хакатона действует [существующий интерфейс доступа](hackathon-access.md): поле кода-приглашения в Android проверяет код на сервере; дополнительных логина/пароля пациента нет. Врач входит через имеющуюся форму логина/пароля. Обе существующие кнопки деморежима и локальные сценарии сохраняются; деморежим не выдаёт серверные полномочия и не отправляет свои факты врачу. Ошибка сети не переключает режим автоматически.

Кэш и очередь разделены по аккаунтам и средам; деморежим не использует рабочую очередь. При выходе отправка прекращается; неотправленные черновики блокируются для другого аккаунта и не перепривязываются автоматически. Отзыв связи проверяется сервером независимо от состояния клиента. Сохранение старого кэша не означает продолжающегося разрешения на серверные операции; офлайн-политика и защита кэша входят в критерии A01.

## 4. Основные потоки

1. **Врач → пациент.** Врач подтверждает план; сервер фиксирует версию, начало действия, изменения/отмены. Android получает разрешённую проекцию и атомарно обновляет кэш/напоминания. Старые факты сохраняют исходную версию назначения.
2. **Пациент → врач.** Android сохраняет факт и исходящую команду одной транзакцией SQLite. API проверяет доступ/версию, сохраняет факт и квитанцию одной транзакцией PostgreSQL. Врач читает ту же карту без переноса данных вручную.
3. **Обращение → ответ.** Обращение и ответ хранятся на сервере. Статусы «на телефоне», «принято сервером», «прочитано врачом» имеют отдельные основания; чтение не означает клинической оценки или действия.

Команда содержит устойчивый commandId, тип/версию схемы, время факта и при необходимости версию плана/слот/версию формы. Patient/clinic определяются сессией. Повтор той же команды возвращает прежний результат; другой payload с тем же ID отклоняется. Сервер возвращает подтверждение, время получения и актуальную ревизию. Клиент не удаляет очередь до подтверждения; после потери ответа повторяет тот же ID. Исправление ссылается на исходный факт и сохраняет историю.

Опросники передаются с исходными ответами, полнотой и версией; пропуски и отказ не становятся нулями. Отметка приёма, завершение анкеты и игровой прогресс — разные факты. Текущие report.add/message.* не используются как обход для отсутствующей семантики доз или анкет.

## 5. Обновление и отказы

Для первой поставки: чтение при открытии, возврате из фона, восстановлении сети и после собственной команды. На открытых рабочих экранах — настраиваемый опрос, стартовый интервал 30 секунд; ошибки дают задержку повторов. Контракт ревизий/условного чтения согласуется в A36. Не обещаем мгновенность или постоянную работу в фоне; отдельная push-инфраструктура не требуется для первого сквозного сценария.

При конфликте плана ввод сохраняется, данные перечитываются, устаревшая команда не переписывает новый план. Смена/отзыв сессии останавливает очередь; сетевой сбой не подменяет данные синтетикой. Напоминания работают по последнему полученному плану с видимым состоянием актуальности; после получения изменения старое расписание пересчитывается.

## 6. Развёртывание и приёмка

На VPS: Caddy:443 → API на loopback → PostgreSQL на loopback. У web и API общий origin; секреты и ключи вне release-архива, постоянные данные вне каталога версии. Согласованный релиз включает совместимые Android/API/web-контракты и проверенное исправление прокси, а не только старый кандидат от 0ae22a1.

Для реальных данных схема дополняется защищёнными сетевыми переходами, шифрованными хранилищами и отдельной границей управления ключами; средства выбираются по медицинскому профилю защиты. Публичный маркетинг отделяется от медицинского origin. Обычные HTTP/SQLite/файловые выгрузки синтетической сборки не переносятся в рабочий контур как приемлемая защита.

Проверяем один синтетический цикл: вход пациента → отчёт/доза/анкета → серверная карта врача → подтверждение нового плана → получение на Android → новые напоминания → обращение/ответ. Затем повторяем с потерей ответа, дублированием, конфликтом версии, перезапуском, чужой клиникой и отзывом доступа. Показатели A08 подключаются отдельно через A06 из этих же разрешённых серверных фактов.

Архитектура не подтверждает доступность VPS: последняя SSH-попытка завершилась timeout. Домен, восстановление доступа, независимое PR-ревью, замечания зависимостей, публикация и резервирование остаются условиями серверного этапа. Реальные пациенты и активация клинических правил в этот синтетический контур не входят.
