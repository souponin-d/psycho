**Задача:** Создать инструмент поддержки принятия врачебных решений для ведения пациентов с тревожно-депрессивной симптоматикой.

## Задачи инструмента

1. Предлагает стандартизированные методы для оценки состояния пациента.
2. Предоставляет рекомендации/справочную информацию по возможным вариантам терапии.
3. Осуществляет учёт и оценку индивидуальных рисков и нежелательных явлений.
4. Обеспечивает мониторинг динамики состояния пациента.
5. Предоставляет пациенту интерфейс для самоотчета и самостоятельного отслеживания динамики состояния.
6. Обеспечивает каналами коммуникации для сопровождения лечебного процесса.
7. Позволяет оценить приверженность пациента лечению и рекомендациям врача.
8. Выявляет ситуации, требующие направления пациента к психиатру (для врачей других специальностей). Предоставляет рекомендации по дальнейшей маршрутизации пациента, исходя из полученных данных (“обязательно” и “желательно”, в зависимости от тяжести состояния).

## Обязательные условия

- Решение поддерживает как минимум две роли: «Врач» и «Пациент» с раздельными функциями и правами доступа.
- Связь “врач-пациент”. Данные пациента связаны с его ведущим лечащим врачом: сведения, которые вводит пациент, попадают в карточку этого пациента у врача без участия третьих лиц.
- Решение не выполняет клинических действий самостоятельно: назначение, изменение и отмена терапии, направление к психиатру и изменение плана лечения происходят только после подтверждения врачом.
- Решение демонстрируется на клинических сценариях, в которых рассматривается назначение препарата «Авиандр». Каждый сценарий включает профиль пациента, рекомендации по лечению и маршрутизацию пациента.
- Должен быть реализован механизм «алертинга»: система самостоятельно определяет критическое состояние пациента по соответствующим признакам (перечень признаков определяет команда), экстренно оповещает врача, производит ряд действий (которые определяет команда).
- Сигналы о направлении к психиатру и предупреждения о безопасности терапии визуально выделены среди прочей информации; категории «обязательно» и «желательно» различимы между собой.
- Решение рекомендует только лекарственные препараты, зарегистрированные в Российской Федерации, в пределах зарегистрированных показаний, противопоказаний и режимов дозирования. Решение о применении вне инструкции может принять только врач.
- Использование клинических рекомендаций, диагностических шкал итп. Клинические рекомендации — действующие, одобренные Минздравом России. Международные рекомендации допускаются для дополнения, с явным указанием источника. Сведения о лекарственных препаратах — по действующей инструкции по медицинскому применению (общей характеристике лекарственного препарата), опубликованной в Государственном реестре лекарственных средств. Психометрические инструменты — валидированные, с валидированной русскоязычной версией. Команда указывает источник валидации и соблюдает условия использования инструмента (авторские права, лицензия).
- Соответствие требованиям законодательства РФ.
- Соблюдение конфиденциальности

## Что будет оцениваться?

1. **Научная обоснованность:** использование шкал, клинических рекомендаций, инструкций и прочее. Их необходимо указать.
2. Клиническая применимость
3. Удобство пользовательского интерфейса
4. Наличие всех обязательных условий
5. Отдельно оценивается каждый пункт из списка “что делает инструмент”
6. Апробация инструмента (с соблюдением законодательства и сохранением конфиденциальной информации)

## Технические метрики

1. **Быстродействие элементов системы** - время отклика интерфейса, время формирования рекомендаций, время доставки алерта врачу с момента поступления критических данных и т.д.
2. **Обработка входных данных** - точность и полнота извлечения ключевых сведений из историй болезни разных шаблонов (различный порядок разделов, уровень детализации, стиль описания, формат фиксации диагнозов и назначений).
3. **Надежность и корректность работы** - количество сбоев при прохождении сценариев, устойчивость к полноте и корректности входных данных.
4. **Эргономика интерфейса** - время и количество действий пользователя при прохождении типовых сценариев
5. **Обоснованность выводов и рекомендаций** релевантными источниками данных, методами, шкалами и т.д., на основе которых они сделаны
6. **Устойчивость к нагрузкам:** сколько пользователей система выдерживает одновременно, как меняется время отклика под нагрузкой
7. **Отказоустойчивость и восстановление данных:** резервное копирование, какой объём данных может быть потерян при сбое, сколько времени занимает восстановление работоспособности системы, не теряются ли критические данные отправленные/полученные во время сбоя
8. Кроссплатформенность
9. Масштабируемость архитектуры
10. **Гибкость архитектуры:** можно ли обновлять/добавлять шкалы, препараты, правила алертинга и новые функции без изменения ядра системы.
11. **Гибкость работы с данными:** структура базы данных, скорость доступа к данным, удобство поиска, возможность фильтровать и делать выборки, можно ли расширять модель данных
12. **Полнота данных** - на сколько модель данных покрывает сущности, необходимые для качественного выполнения задач инструмента
13. Защищенность данных
