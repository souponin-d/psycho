# Единый клинический контекст врача

Этап MI01 в ветке `codex/doctor-major-update`. Рабочий контур — синтетические карты; интеграция с приложением пациента остаётся отдельным этапом. [План реализации](superpowers/plans/2026-10-26-clinical-context.md).

## Что доступно врачу

В обзоре карты, приёме и контексте лекарственного назначения используется один реестр: диагнозы/гипотезы, соматические заболевания, лекарства и аллергии. Новый факт создаётся кнопкой «Добавить клинический факт». Диагноз и соматика выбираются из [МКБ-10](icd10-catalog.md), лекарство — из [ГРЛС](grls-catalog.md) с регистрационным снимком. Сведения о фактическом приёме лекарства не создают назначение.

Каждый факт хранит происхождение: пациент, документ этой карты, врач, родственник или прежняя запись. Сохраняются описание источника, исходная цитата и дата получения; неизвестная дата остаётся пустой. Для документа проверяются принадлежность текущей карте, отсутствие исключения и буквальное наличие цитаты. Автор записи и время изменения фиксируются системой.

Сохранение создаёт статус «Не проверено», а неизвестное значение — «Неизвестно». Отдельным решением врач подтверждает факт, отмечает необходимость уточнения, противоречие или переводит его в историю. Подтверждение не требует свободного текста; противоречие и перевод в историю требуют причины. Подтверждение диагноза защищено полномочием психиатра на сервере.

Исправление требует причины, добавляет версию и снимает подтверждение только с нового значения. Все прежние версии, источники, авторы и решения остаются доступны в «Источник и история». Неактуальный факт не удаляется; новое актуальное сведение оформляется отдельным фактом. Отсутствие данных об аллергии не равно её отрицанию: явное отрицание имеет отдельное значение и собственный источник.

## Совместимость прежних записей

Старые поля профиля, эпизоды, диагнозы приёмов и назначения сохраняются. Раздел «Прежние сведения для разбора» показывает их без автоматического подтверждения и угадывания кодов. При разборе сохраняется исходный структурированный снимок `origin.legacyContent`; повторный перенос той же исходной записи блокируется, а изменившийся источник снова показывается для сверки. Изменения старого поля не переписывают проверенный факт.

Неразобранный свободный текст можно сохранить в реестре, но нельзя подтвердить без структурирования. Назначение в плане не доказывает фактический приём. Если документ-источник позднее исключён или изменён, интерфейс требует новой сверки применимости; прежнее подтверждение сохраняется как историческое решение.

## API и хранение

Дополнительное поле `PatientRecord.clinicalFacts` содержит записи `{ id, versions }`; каждая версия включает `content`, `origin`, `status`, `changedAt`, `changedBy`, `verifiedAt`, `verifiedBy`, `reason`. Поле необязательное для совместимости старых карт. Хранится в существующем JSON-документе PostgreSQL; отдельная миграция таблиц не требуется. Локальный режим использует ту же модель в IndexedDB.

Команды через существующий `POST /api/patients/{id}/commands`:

```json
{
  "commandId": "unique-command-id",
  "expectedRevision": 0,
  "mutation": {
    "type": "fact.save",
    "value": {
      "id": "unique-fact-id",
      "expectedVersion": 0,
      "content": {
        "category": "allergy",
        "state": "known",
        "substance": "Учебный аллерген",
        "reaction": "Синтетическое описание"
      },
      "origin": {
        "kind": "patient",
        "reference": "Учебная беседа",
        "quote": "Пациент сообщил об учебной реакции",
        "observedAt": ""
      },
      "reason": ""
    }
  }
}
```

`fact.review` принимает `id`, `expectedVersion`, `decision` (`confirm`, `clarify`, `contradict`, `unknown`, `inactivate`) и `reason`. Для исправления повторно используется `fact.save` с текущей версией и причиной. Клиент не присылает готовую историю или авторство подтверждения: подмена полей отклоняется. Ревизия карты и версия факта защищают от потери параллельных изменений; повтор команды идемпотентен. Оба вида команд записываются в аудит.

Сервер сохраняет существующие проверки врачебной сессии, CSRF, клиники и связи врача с пациентом. Пациентский API не позволяет выполнять эти команды и не выдаёт внутренний реестр. [OpenAPI](contracts/doctor.openapi.json) и клиент генерируются командой `npm run contract:doctor`.

Изменение версии или статуса факта делает подготовительную лекарственную проверку Авиандра устаревшей. Это проверка актуальности снимка, без активации клинических правил, назначения или отмены препаратов.

## Обновление и откат

Обновлять API и web вместе из одной ветки: старый API не понимает новые команды. Перед заменой версии выполнить стандартное резервное копирование синтетической БД. При откате старый интерфейс не покажет реестр; нельзя перезаписывать карты старым клиентом с удалением неизвестных ему полей. Историю `clinicalFacts` сохранять при откате, не преобразовывать её обратно в свободный текст.
