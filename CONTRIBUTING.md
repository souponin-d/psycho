# Совместная работа

## Ветки и задачи

1. Создай задачу с целью и проверяемым результатом либо выбери существующую.
2. Обнови локальный `main` и создай отдельную ветку для задачи: `feat/…`, `fix/…` или `docs/…`. Для агентских изменений используется `codex/…`.
3. Делай небольшие изменения, которые можно проверить и обсудить отдельно.
4. Перед PR выполни `npm run check`. Форматирование исправляется командой `npm run format`.
5. В PR опиши результат, способ проверки и приложи скриншот, если изменился интерфейс.
6. После успешных проверок и просмотра другим техническим участником выполни squash merge. Если технический участник один, проверь diff перед слиянием самостоятельно.

При первом клонировании и после изменения `package-lock.json` выполняй `npm ci --ignore-scripts`. Добавляй новые devDependencies с точной версией и обновляй lockfile вместе с `package.json`.

## Материалы и прототипы

- Подготовительный документ отражает состояние сведений на указанную в нём дату. Новые условия сохраняй в [официальных материалах](docs/official/README.md), связывая требование с источником.
- Идею оформляй как гипотезу: пользователь, проблема, сценарий, ожидаемая польза и способ проверки. Шаблон находится в [каталоге идей](docs/ideas/README.md).
- Прототип должен иметь воспроизводимый запуск, вымышленные демонстрационные данные и явные границы того, что действительно работает.
- Принятые решения записывай в [журнал](docs/decisions/README.md), чтобы следующий участник понимал причину выбора.
- Перед добавлением материалов проверь разрешение на их распространение. Ключи и локальные настройки храни в `.env`; в примерах используй пустые значения. Реальные сведения о пациентах в демонстрационных материалах не используются.

## Настройка GitHub

После первого успешного запуска workflow владелец репозитория может настроить правило для `main` в **Settings → Rules → Rulesets** либо доступную защиту ветки:

- разрешить изменения через PR;
- сделать обязательными `Repository checks (ubuntu-latest)` и `Repository checks (windows-latest)`;
- потребовать разрешения обсуждений перед слиянием;
- запретить force push и удаление `main`;
- при двух технических участниках потребовать одно одобрение, при одном оставить ревью добровольным.

Доступность правил зависит от типа репозитория и тарифа GitHub. Файл workflow сам по себе не включает защиту ветки. Руководство: [правила репозитория](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets).

## Расширение проверок

Когда появится приложение, добавляй проверки его реального поведения в `npm run check` и сохраняй единую точку запуска для CI. Для новых инструментов укажи команды и системные требования в README. При появлении lifecycle-скриптов зависимостей отдельно пересмотри установку с `--ignore-scripts`.
