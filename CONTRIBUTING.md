# Совместная работа

## Обязательное правило main

**Прямой push в `main` запрещён всем участникам и ИИ-агентам. Любое изменение попадает в `main` только через pull request с проверками и независимым одобрением.** Нельзя обходить это правило локальным merge с последующим push, административным bypass, отключением проверок или force push. Удаление `main` запрещено.

[AGENTS.md](AGENTS.md) содержит инструкции для агентов. [План пяти участников](docs/superpowers/plans/2026-10-19-five-contributor-development.md) определяет ответственность, зависимости и порядок интеграции.

Перед первой задачей пройди [подготовку рабочего места для своей роли](docs/team/local-development-setup.md). Общие проверки участникам 2–5 доступны без .NET, Docker и мобильных SDK; запуск будущих компонентов требует подготовленного P01a.

## Ветки и задачи

[Стартовые issues, порядок и распределение ролей](docs/team/backlog.md). Оперативные статусы и assignees ведём в GitHub Issues: `status:ready`, `status:in-progress`, `status:in-review`, `status:blocked`. Одновременно используется одна статусная метка; закрытие issue отмечает выполненную или явно отменённую задачу. Markdown хранит план и ссылки.

1. Создай issue по шаблону «Задача»: результат, ответственный участник, границы файлов/модулей, зависимости, критерии приёмки и проверки. Привяжи требования F/M/E/T из официального кейса, если они затрагиваются.
2. Получи актуальные изменения и создай ветку от `origin/main`. Используй `feat/<issue>-<topic>`, `fix/…`, `docs/…`, `chore/…`; для ИИ-агентов — `codex/<issue>-<topic>`. Одна ветка соответствует одной задаче, а не всему направлению участника.
3. До реализации согласуй изменения общих контрактов, схемы БД и механизмов доступа с главой разработки. Не начинай зависимые ветки от незавершённого PR без явно записанной зависимости; по умолчанию зависимость сначала сливается в `main`.
4. Открывай draft PR рано, чтобы показать границы работы и занятые файлы. Незавершённость, мокапы и временные решения отмечай явно.
5. Перед передачей на ревью изучи весь diff и выполни проверки. Ответственность за результат остаётся у человека, даже если весь код написал ИИ.

Глава разработки реализует backend, мобильное приложение и ключевые механизмы. Участники 2–5 получают небольшие поддерживающие задачи, а не приложения целиком. В issue перечисляются разрешённые файлы, готовые входы/выходы и класс проверки A/B/C из командного плана. Если требуется новый API, зависимость, изменение схемы/прав или клиническое решение, не расширяй задачу самостоятельно: выдели этот вопрос главе разработки.

Основной вклад всех пяти участников — изменения в репозитории через PR: 2 — компоненты веба врача; 3 — компоненты дашборда; 4 — небольшие общие веб-компоненты; 5 — синтетические данные, страницы примеров и небольшие UI-исправления. CustDev проводится отдельно всей командой. Следующая небольшая задача выдаётся после принятия предыдущего PR.

Размер задачи — один наблюдаемый результат, который можно независимо проверить. Ориентир PR — до 400 строк вручную написанных изменений; это не жёсткий лимит. Больший PR объясни в описании. Сгенерированные файлы и lockfile учитываются отдельно. Не разрывай миграцию, контракт и обязательную адаптацию потребителей на несовместимые слияния ради размера.

При первом клонировании и после изменения `package-lock.json` выполняй `npm ci --ignore-scripts`. Добавляй новые devDependencies с точной версией и обновляй lockfile вместе с `package.json`. Не меняй менеджер пакетов без отдельного решения.

## Оформление pull request

- База — `main`; источник — ветка задачи. Используй [шаблон PR](.github/pull_request_template.md).
- Заголовок: `тип(область): результат`, например `feat(doctor): показать историю измерений` или `docs(team): распределить задачи участников`. Типы: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `ci`.
- Укажи `Closes #номер`, участника-владельца, требования кейса и другие PR, от которых зависит работа. До появления issue не выдумывай его номер: напиши «issue ещё не создан» и создай его до ready for review.
- Опиши наблюдаемое поведение, границы изменения, команды и фактические результаты проверок. Для интерфейса приложи скриншоты или запись; для API — пример запроса/ответа без медицинских данных; для миграции — порядок применения и восстановления.
- Отдельно укажи изменения прав доступа, клинических правил/источников, контрактов и зависимостей. Для клинического содержания приложи запись содержательной проверки, а не только ссылку на статью.
- Укажи оставшиеся ограничения. Не выдавай синтетическую демонстрацию за клиническую апробацию, а успешную сборку — за проверку сценария.

## Проверки, ревью и слияние

1. Автор проверяет весь diff, выполняет `npm run check` и дополнительные проверки изменённых модулей. Сейчас общая команда проверяет только документацию и лендинг; продуктовые проверки добавляются в первой инфраструктурной задаче плана.
2. Ready for review означает: критерии issue выполнены, нет необозначенных заглушек, приложены свидетельства проверки. Draft PR не сливается.
3. Нужен минимум один approve от другого контрибьютора. Самопроверка автора, второй чат того же автора или сообщение ИИ-ревьюера не заменяют одобрение другого участника репозитория.
4. Общие контракты, доступ, клиническое ядро, миграции, развёртывание и CI проверяет глава разработки. Если он автор, независимую проверку делает другой участник по зафиксированным контрактам и инвариантам. Клинические правила до активации дополнительно проверяет клиницист; авторство главой разработки это не заменяет.
5. Ревьюер повторяет основной сценарий и существенные отрицательные проверки. Блокирующие замечания устраняет автор; обсуждение закрывает проверивший исправление ревьюер. Новые изменения требуют повторного ревью затронутой части.
6. Перед merge должны пройти обязательные checks актуального PR, разрешиться блокирующие обсуждения и сохраниться действующее независимое одобрение. Конфликты устраняй в ветке задачи, затем повторяй проверки.
7. Слияние выполняется через GitHub PR с **squash merge**. Его может выполнить участник с правом merge после выполнения условий; только авторское одобрение недопустимо. После merge ветка задачи удаляется. Прямой push в `main` не используется даже для срочного исправления.

Проверка соразмерна изменению: для материала достаточно шаблона, ссылок/валидатора и общих checks; для пассивного UI — типов/сборки и просмотра заданных состояний. Отдельные тесты, повторяющие статическую разметку, не требуются. Мобильная логика, доступ, клинические действия, вычисления, события и хранение требуют полноценных проверок главы разработки. Независимый проверяющий его PR получает конкретный сценарий и свидетельства; если он не может оценить критичный пункт, это фиксируется вместо формального approve.

Для отката создаётся отдельный revert PR с описанием причин и проверками. Откат миграций и потерю данных оценивают отдельно; `git reset` и force push в `main` не являются способом отката релиза.

## Материалы и прототипы

- Подготовительный документ отражает состояние сведений на указанную в нём дату. Новые условия сохраняй в [официальных материалах](docs/official/README.md), связывая требование с источником.
- Идею оформляй как гипотезу: пользователь, проблема, сценарий, ожидаемая польза и способ проверки. Шаблон находится в [каталоге идей](docs/ideas/README.md).
- Прототип должен иметь воспроизводимый запуск, вымышленные демонстрационные данные и явные границы того, что действительно работает.
- Принятые решения записывай в [журнал](docs/decisions/README.md), чтобы следующий участник понимал причину выбора.
- Перед добавлением материалов проверь разрешение на их распространение. Ключи и локальные настройки храни в `.env`; в примерах используй пустые значения. Реальные сведения о пациентах в демонстрационных материалах не используются.

## Настройка GitHub

Это действие владельца/администратора GitHub-репозитория. **Наличие AGENTS.md, шаблона PR или workflow не запрещает push технически. В рамках подготовки документов настройки удалённого репозитория не изменялись.**

В **Settings → Rules → Rulesets** создай активное branch ruleset для `main` либо настрой эквивалентную защиту ветки:

- точная целевая ветка — `main`, статус правила — Active;
- обязательный pull request перед merge, минимум **1 approving review**;
- сброс устаревших approvals при новых изменениях и одобрение последнего набора изменений другим участником;
- обязательное разрешение обсуждений;
- обязательные checks `Repository checks (ubuntu-latest)` и `Repository checks (windows-latest)` после их первого появления; перед выбором проверь реальные имена в GitHub;
- актуальность ветки относительно `main` перед merge;
- запрет удаления ветки и force push;
- пустой список bypass: не добавляй администраторов, участников, ботов и GitHub Apps для обхода этих правил. Для classic branch protection включи применение правил к администраторам;
- в настройках pull requests репозитория оставь squash merge как принятый способ слияния.

Дополнительное ревью главой разработки пока является командным правилом: соответствие GitHub-аккаунтов ролям 2–5 ещё не назначено, поэтому фиктивный `CODEOWNERS` не создаётся. До включения обязательного code-owner review назначь для общих технических областей минимум двух допустимых проверяющих: автор PR не может одобрить собственные изменения. Не делай главу разработки единственным обязательным code owner для его собственных PR. Клиническое одобрение фиксируется отдельно.

Владелец проверяет активные серверные правила и записывает дату/результат в issue настройки репозитория: `main` действительно охвачена обязательным PR без bypass, PR без approve или с красным обязательным check нельзя слить, разрешённый PR проходит squash merge. Для подтверждения приложи снимок/экспорт действующих правил и результат легитимного PR. `git push --dry-run` не считается проверкой GitHub-защиты: сервер может не выполнять проверку ruleset в этом режиме. Запрещённый прямой push не используется как тест. Подтверди применение правила к пяти аккаунтам и используемым ботам.

Доступность rulesets и обязательных проверок зависит от типа репозитория и тарифа GitHub. Если функция недоступна, зафиксируй ограничение и согласуй доступный способ серверной защиты; не объявляй организационный запрет технически включённым. Руководство: [правила репозитория](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets).

Проверка 19 октября 2026 года: репозиторий приватный, `main` имеет `protected: false`; API защиты/rulesets отвечает `403` с требованием GitHub Pro или публичного репозитория. Это отдельный блокер P00. Подготовка ветки и PR не включает смену тарифа, видимости или автоматическое включение недоступных правил. Организационный запрет прямого push сохраняется.

Workflow сохраняет запуск на push в `main`, чтобы проверять уже слитые PR. Этот триггер не разрешает прямой push.

## Расширение проверок

`npm run check` остаётся общей проверкой репозитория на Node.js: документация, форматирование и текущие общие проверки. В P01a добавляются отдельные `check:web` и `check:fixtures`, не требующие .NET, БД или мобильных SDK. Реальное поведение API проверяется отдельной `check:api`, мобильного приложения — отдельной `check:mobile` по мере создания этих модулей. CI запускает применимые команды отдельными обязательными jobs; единый локальный вызов всех SDK участникам 2–5 не требуется. Для новых инструментов укажи реальные команды и системные требования в README. При появлении lifecycle-скриптов зависимостей отдельно пересмотри установку с `--ignore-scripts`.
